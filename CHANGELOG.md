## 2026-09-22 — Журнал J6: поиск и архив

Схема не менялась: ни хранилищ, ни индексов, ни подъёма `DB_VERSION`.

**Поиск** — `CWJournal.search.run(query, { includeArchive, resolveCommunity,
labelVisit })`: только чтение, по требованию, в памяти — узлы и записи
читаются один раз за прогон. Сохранённого индекса, истории запросов и кэша
открытого текста нет нигде (граница J8); запрос не попадает ни в хэш, ни в
историю браузера, ни в localStorage — живёт в памяти экрана. Нормализация:
регистр, `ё ≡ е`, латинские диакритики, `ß→ss`, `ł→l`; `й/ї/ґ` не
сворачиваются. Несколько слов — «И»; хотя бы одно слово должно быть в
собственном тексте (у посещения — в подписи/датах), остальные могут
совпасть с контекстом район › собрание › группа. Ранг: поле целиком →
начало поля → подстрока → свежее `updatedAt` → id. Название, номер, адрес
и контакт из CWDirectory участвуют только в памяти; без справочника
работает локальная подпись узла. Строка с `sec` текстом не ищется —
только считается («защищённые записи не искались: N»).

Экран «Поиск» (эталоны 07-search-m/d): поле с очисткой, фильтры со
счётчиками, группы «Визиты / Записи и проекты / Задачи / Районы и
собрания», отрывок с подсветкой (`<mark>` + `textContent`, пользовательский
текст не проходит через `innerHTML`), крошки контекста, пустое состояние и
«ничего не найдено». Архивный контекст по умолчанию исключён и
открывается фильтром «Архив». Устаревший ответ отбрасывается по номеру
прогона. Кнопка поиска в шапке ставит фокус в поле.

**Архив** — `status`/`archivedAt`, не хранилище. Узел: новые
`nodes.archive()` / `nodes.unarchive()` (восстановление физически удаляет
`archivedAt`); прямой патч статуса через `nodes.update` отклоняется
(`journal-node-use-lifecycle`), меню дерева переведены на цикл. Посещение —
прежние `visits.archive/unarchive`. Архивность «в контексте» (узел, предок,
посещение-источник) вычисляется при чтении и не пишется; выполненная
задача и закрытый перенос архивом не являются. `CWJournal.archive.list()`
— только напрямую архивные узлы и посещения, новые сверху; легаси-узел без
`archivedAt` не теряется; объект с архивным предком помечен. Экран
«Архив»: вкладки, дата архивации, «Восстановить» (только выбранный объект,
без каскада), переход к объекту; удаления нет.

Новая проверка `check-journal-search-archive.mjs` в гейте;
`check-journal-db.mjs` переведён на цикл архива узла. Неиспользуемые
ключи `j.placeholder.*` удалены.

**Версии:** Журнал `0.7.0 → 0.8.0`; патч-бамп общего слоя: хаб
`0.41.45 → 0.41.46`, Конгрессы `4.46.67 → 4.46.68`, Школа пионеров

## 2026-09-22 — Журнал J5: задачи и перенос «на следующее посещение»

Схема не менялась. **Перенос** — `CWJournal.carry`: запись посещения
(заметка, наблюдение, вопрос, задача) помечается «На след. визит» в
посещении-источнике; это та же строка `journalEntries`, между посещениями
она не копируется и не переподчиняется (`fields.visitId` остаётся
источником). Открытый пункт несёт `carryKey = '<nodeId>:open'`; закрытый —
поля НЕТ физически: закрытие переписывает запись целиком через
`mutate()` общей базы (`replaceEntry`), `null`/`''`/`false` не пишутся.
История — `touches[]`: `{ visitId, at, action }`, `raised | kept |
deferred | closed`, без текста пользователя. В более позднем посещении того
же узла пункт входящий: «Закрыть», «Оставить открытым», «Перенести дальше».
Поднятый в самом посещении пункт входящим для него не считается — он
в строке «Помечено на следующее посещение», которая теперь настоящая.
Решение принимается только в открытом посещении; посещение, на которое
ссылается история переноса, не удаляется (`journal-visit-has-carry`).

**Задачи** — единый цикл todo `CWJournal.tasks` для задач посещений и
самостоятельных задач узла (район, собрание, группа, предгруппа):
создание, правка текста, необязательный срок (`dueDate`, верхнее
индексируемое поле; снятие срока удаляет поле), выполнение/возврат,
удаление без связей. `visitRecords.complete/reopen` делегируют этому циклу.
Задача завершённого или архивного посещения — только чтение и на экране
«Задачи» (правило в слое данных). Порядок: открытые — со сроком раньше,
ранний срок первым, затем создание; выполненные — свежие первыми. Экран
«Задачи» стал рабочим: «Открытые/Выполненные», контекст район › узел
(и сезон посещения), явный выбор области при создании.

Общий фасад `CWJournal.entries` больше не создаёт, не правит и не удаляет
задачи (`journal-task-use-facade`) и не трогает `carryKey`/`touches`
(`journal-carry-use-facade`). Контрольные прогоны: без этих стражей — 8
провалов обхода; закрытие через слияние с `carryKey: null` — 4 провала.

Эталон `05-carryover-m.jpg`: поле «Комментарий к решению» не заведено —
текст в `touches[]` стал бы вторым каналом открытого текста вне `body`
(граница J8). Попутно: `[hidden]` внутри модуля теперь всегда скрывает —
общие `.md-banner/.md-btn/.md-field` перебивали его (пустой баннер переноса
и кнопка удаления в диалоге задачи были видны).

Новый гейт `scripts/check-journal-carry-tasks.mjs`. Проверки J2 для
индексов `carryKey`/`type` заводят строки на уровне `CWDB`: общий фасад
такие строки больше не создаёт.

**Версии:** Журнал `0.6.0 → 0.7.0`; хаб `0.41.44 → 0.41.45`; патч-бамп
кэш-фёрст оболочек из-за правки `shared/version.js`: Конгрессы

## 2026-09-22 — Журнал J4b: записи посещения

Редактор экрана посещения стал настоящим: заметки, наблюдения, вопросы и
задачи ведутся прямо в посещении (эталоны `04-visit-m/-d.jpg`). Схема не
менялась: записи — строки `journalEntries` с `fields.visitId`, доступ только
через новый `CWJournal.visitRecords` (`get/byVisit/add/update/convertToTodo/
complete/reopen/remove`).

Контракт: `nodeId/circuitId/fields.visitId` берутся из посещения (подделать
их аргументами нельзя) и неизменяемы. Текст пользователя — только
верхнеуровневый `body`; `fields` несёт лишь `{ visitId, format, seq }` — без
копии текста и без HTML (граница J8: защищённый `body` позже уйдёт в `sec`).
Оформление — канонический enum `paragraph|heading2|list|quote`, у задачи
`checklist`. Задача переключается `open ↔ done` только через
`complete/reopen`; превращение текстовой записи в задачу — явный
`convertToTodo` (кнопки «Сделать задачей», «В задачу», «Галочки»). Править
записи можно только в открытом посещении: завершённое и архивное — только
чтение, правило держит слой данных (`journal-visit-readonly`). Порядок —
`fields.seq` (номер создания), затем `createdAt`, затем `id`. Удаление
записи со связями отклоняется; посещение с записями по-прежнему не
удаляется (`journal-visit-has-entries`).

Тот же класс обхода, что закрывали в J4a, закрыт и для записей посещения:
общие `entries.add/update/remove` не создают, не правят и не удаляют их и не
могут «приписать» обычную запись к посещению
(`journal-visit-record-use-facade`).

Интерфейс: блок правится по клику (янтарная рамка эталона), сохранение явное,
без автосохранения; панель форматов без выбранного блока начинает новую
запись в этом формате. «На след. визит» (J5) и «Связать» (J7) видимы и
неактивны. «Итоги визита» показывают реальное число открытых и выполненных
задач; строка переноса нейтральна до J5.

Новый гейт `scripts/check-journal-visit-records.mjs` (79 проверок) с
контрольными прогонами: без стража общего фасада проваливаются 8 проверок
обхода, с `data.js` до J4b гейт не проходит. Тесты J4a переведены с
общего фасада на `visitRecords` там, где они создавали записи посещения.

**Версии:** Журнал `0.5.0 → 0.6.0`; хаб `0.41.43 → 0.41.44`; патч-бамп
кэш-фёрст оболочек из-за правки `shared/version.js`: Конгрессы

## 2026-09-22 — Журнал J4a: посещения и экран посещения

Посещение — строка `journalEntries` с `type:'visit'` (пятого хранилища нет,
схема не менялась), доступ только через новый `CWJournal.visits`. Родитель —
собрание, группа или предгруппа; `type/nodeId/circuitId` неизменяемы; даты
`dateFrom/dateTo` в формате `YYYY-MM-DD`, окончание не раньше начала,
пересечение посещений одного узла допускается. Статус: `open ↔ completed`,
любой → `archived` с `archivedAt` (возврат к прежнему статусу) — только
через `complete/reopen/archive/unarchive`, не через `update()`. Удаление
отказывает, пока у посещения есть записи (`fields.visitId`, контракт для
J4b) или связи — безопасная альтернатива архив.
Граница держится в самом слое данных: общий фасад `CWJournal.entries`
посещения не мутирует — `add({type:'visit'})`, `update()` и `remove()`
посещения отклоняются с `journal-visit-use-facade` (без молчаливого
перенаправления), так что обойти инварианты через официальный фасад нельзя.
Чтение через `entries.*` не ограничено.

Маршрут: `#districts/<c>/congregation/<n>/visits` (вкладка «Посещения») и
`…/visit/<v>` (экран посещения). Разбор вынесен в `journal/js/route.js` —
чистая функция под тестом; роутер один. Неизвестное или чужое посещение и
неполный хвост маршрута ведут к вкладке «Посещения» собрания, битые id
района/собрания — к списку районов.

Вкладка «Посещения» собрания стала рабочей: реальный список (новые сверху),
пустое состояние, FAB «Визит» с диалогом дат. Экран посещения по эталонам
`04-visit-m/-d.jpg`: крошки район → собрание → сезон, заголовок «Визит —
весна 2028» и диапазон дат (производные от `dateFrom`, не хранятся),
контекст в подстроке топбара, действия в меню «Ещё» (даты, завершить/
возобновить, архив, удалить). Намеренно без фиктивных данных: чип Клиндария
не показывается (связь — J9), вместо него — статус посещения; баннер
переносов скрыт (J5); редактор показан каркасом с неактивной панелью и
нейтральным пустым состоянием (J4b); строка связи с проектом отсутствует (J7).

Попутно: FAB модуля не прятался атрибутом `hidden` (общее
`.md-fab { display: inline-flex }` перебивало `[hidden]`) и ссылки крошек
красились системным синим — обе правки только в `journal/css/styles.css`.

Новый гейт `scripts/check-journal-visits.mjs`: создание, даты, правка и
неизменяемые поля, порядок по узлу, жизненный цикл, безопасное удаление,
разбор маршрута, граница UI ↔ данные (нет прямого `CWDB` в `app.js`),

## 2026-09-21 — Журнал J3b: экран собрания + связь с CWDirectory

Экран собрания стал реальным: маршрут `#districts/<circuitId>/congregation/<nodeId>`,
карточка идентичности с четырьмя состояниями — LINKED (собрание связано с
общим справочником CWDirectory), UNLINKED (локальная запись Журнала без
связи), BROKEN (сохранённый `communityId` не разрешился в справочнике —
ссылка не стирается молча, доступно пересвязывание) и UNAVAILABLE
(справочник не прочитан — связь не трогается и не считается разорванной;
готовность берётся из `CWDirectory.ready`). Дочерние группы/предгруппы того
же собрания переиспользуют дерево J3a без второй реализации CRUD.

Переименование узла идёт через один диспетчер для всех входов (строка
района, топбар собрания, топбар района): связанное собрание показывается
под именем из CWDirectory, поэтому «Переименовать» открывает правку общей
идентичности; несвязанное/разорванное/недоступное собрание, район, группа
и предгруппа переименовываются локально (`label` узла).

Граница зафиксирована архитектурно (`shared/directory.js`, решение
16.08.2026) и здесь только соблюдена: CWDirectory владеет идентичностью
(название/номер/адрес/контакт), Журнал — расписанием встреч в собственном
поле `fields.schedule` узла. Правка связанной идентичности вызывает
`CWDirectory.upsert()`, правка расписания — только `CWJournal.nodes.update()`;
ни одна из операций не задевает границу другой (проверено тестом).

Добавлен `CWDirectory.create()` (`shared/directory.js`) — минимальное
расширение для записей без заранее известного id (в отличие от Клиндария,
который зеркалит собственный `event.id`). Генерации id внутри не появилось:
обёртка вызывает существующий `CWDB.communities.add()` без id, который сам
пользуется `uid('com')` из `shared/db.js`, и просто забирает готовый id для
кэша/индекса/маячка `cw-directory-rev` — тем же путём, что и `upsert()`.

Связывание с существующей записью требует явного подтверждения человеком
(клик по конкретному кандидату) — автоматического применения слабых/
неоднозначных совпадений нет. Создание новой записи и последующее
связывание рассматриваются как одна операция с точки зрения пользователя:
если `CWDirectory.create()` успел записать карточку, а сохранение
`communityId` на узле Журнала не удалось, узел `detach()`-ается из
созданной записи, чтобы не остался осиротевший справочный элемент, который
не знает ни один модуль.

## 2026-09-21 — Журнал J3a: реальное дерево района

Статическая фикстура «Район» (J1) заменена настоящим деревом на
`CWJournal`/`journalNodes`: районы → собрания → группы/предгруппы. Экран
Обзора остаётся фикстурой — вне рамок этой фазы.

Реализовано: список районов с пустым состоянием (без автосоздания примера);
создание района/собрания/группы/предгруппы через общий диалог
(`.md-dialog`, тот же паттерн, что в «Документах»); переименование,
архив/восстановление, удаление через строчное меню (`.md-menu`, тот же
примитив, что в Конгрессах/Документах); ручной порядок соседей (▲/▼,
обмен `sort`). Иерархия (`kind` ↔ `parentId`) проверяется в
`CWJournal.nodes.add/update`, а не только в интерфейсе: невалидную
комбинацию (группа под районом, собрание под собранием и т.п.) нельзя
завести в обход экрана. Удаление отказывает, если у узла есть дети,
собственные записи или связи — каскадного удаления в этой фазе нет.
`parentId` корня — строка `'root'` (`CWJournal.ROOT_PARENT`), не `null`:
null/undefined не являются валидным ключом IndexedDB (тот же класс
инварианта, что `carryKey` в J2).

Попутно найден и исправлен реальный баг J1: `.j-tag--link` ссылался на
необъявленный нигде токен `--cw-teal` (внутри неразрешимый `var()` делает
всё объявление `color` недействительным) — `journal` просто отсутствовал в

## 2026-09-20 — Hotfix: невалидный легаси Клиндария больше не становится App.state.app

Живой прогон в реальном Chrome нашёл дыру, которую предыдущий гейт
пропустил: структурно чужой легаси (`{"foo":"bar"}`) корректно НЕ мигрирует
на первом запуске — но `load()` уже к тому моменту скармливал ЛЮБОЙ
распарсенный легаси в `migrate()`/`normalizeApp()`, ДО того, как решение
«мигрировать или нет» вообще проверяло его форму. `normalizeApp()` всеяден
и превращал `{foo:'bar'}` в «валидные данные приложения» вместе с `foo` —
обычный runtime, сохраняя это состояние (в реальном Chrome — где именно,
не важно: любой из полусотни вызовов `save()`), заносил `foo` в канон.
На следующем запуске уже исправленная в прошлом hotfix'е ветка «канон уже
существовал» видела валидный канон и удаляла легаси — единственную
сохранившуюся копию.

**Root cause, `circuit-planner/app.js`, `load()`:** валидность легаси
(`isValidPersistedState()`) теперь проверяется ОДИН РАЗ, до присвоения
`App.state.app`, и используется дважды — и для решения «доверять ли
`migrate()`», и для решения «переносить ли в канон» ниже. Невалидный легаси
теперь никогда не становится состоянием приложения: вместо него —
`createDefaultData()`, чистый дефолт без единого поля из легаси.

Отдельно (второй root cause из прошлого прогона аудита, который на самом
деле НЕ доехал до предыдущей поставки: origin/main нёс только
однобокую проверку) — ветка «канон уже существовал» тоже переписана: легаси
удаляется, только если ОБЕ стороны — и канон, и заново прочитанный
легаси-ключ — по отдельности проходят `isValidPersistedState()`.

Регресс расширен полным сценарием в два запуска (свежий контекст, не
повторный вызов `load()` в той же вкладке): проверяется явно, что `foo`
отсутствует и в `App.state.app`, и в каноне — и после первого запуска, и
после второго; тест воспроизводит реальный баг на неисправленном коде
(проверено намеренным откатом файла к `origin/main` перед фиксом — 7
ассертов падали именно так, как в живом Chrome).

**Версии:** Клиндарий `9.94.15 → 9.94.16`. Конгрессы не тронуты — `4.46.60`.
`shared/state.js` не тронут.

`node scripts/check-all.mjs`: 0 FAIL, 0 SKIP (3 прогона подряд).
