## 2026-09-02 (шестой заход) — Документы: полноценный выбор языка документа и rich text для сопроводительных писем

**Версии:** Документы `1.9.2 → 1.10.0` (minor — новый функционал). Правка
`shared/templates/builtin.js` — это правка общего слоя, патч-бамп подтверждён
явным прогоном `check-shared-bump.mjs` с `CW_BUMP_BASE=HEAD` (не
предполагался): хаб `0.41.13 → 0.41.14`, Конгрессы `4.46.35 → 4.46.36`,
Школа пионеров `1.14.13 → 1.14.14`, Назначения `5.5.52 → 5.5.53`. Клиндарий
не в списке — stale-while-revalidate, подтверждено тем же прогоном.

Две независимые UX-функции, обе доведены до полной реализации после
диагностики без слепого кода.

- **Выбор языка документа.** Плоский chip-набор `#edLangs`, строившийся из
  `Object.keys(tpl.translations)`, заменён на выпадающее меню (`.md-menu`,
  тот же примитив, что уже использует меню «Вставка») с фиксированным
  списком всех пяти языков проекта — порядок `UK/RU/DE/PL/EN`. Раньше при
  одной колонке (например, только RU у builtin) пользователь видел
  единственный вариант и не мог создать перевод на другой язык вовсе.
  `CWTemplates.save()` (`shared/templates.js`) уже мёржил новый язык в
  `translations` без удаления остальных — этого оказалось достаточно,
  правка полностью в `documents/js/app.js`/`documents/index.html`. Выбор
  ещё не существующего языка просто переключает `state.lang`; реальная
  запись появляется только по явному Save. Меню различает «перевода нет»
  (колонка существует, но пуста) от «новый перевод» (колонки ещё нет)
  текстом подписи пункта — без нового сложного UI. Это язык документа, не
  язык интерфейса — не связан с `CWDocLang`/`CWI18n`.
- **Rich text для трёх email-body шаблонов** (`sys.visit.congregation.email`,
  `.group.email`, `.pregroup.email`) — единственные три id, переведённые
  `format:'text' → 'html'` в `shared/templates/builtin.js`. Все остальные
  text-шаблоны (salutation, конгрессы, школа) не тронуты.
  `execCommand('bold'/'italic'/'underline')` подтверждён рабочим реальным
  WebKit-рендерером (программная Selection/Range + execCommand,
  `success:true`, реальный `<b>`/`<i>` в результате) — не переписывался.
- **Lazy migration, не destructive.** `shared/templates.js`/`effective()` не
  тронуты — решение целиком локально в Documents. Новый
  `RTE_MIGRATION_IDS` принудительно считает `isHtml()===true` для этих трёх
  id независимо от сырого `tpl.format` (который у существующих
  пользовательских override мог остаться `'text'` от старой версии builtin).
  `needsLazyHtmlMigration()` — точная развилка: конвертировать через уже
  существующий `plainToHtml()` нужно только когда сырой формат ещё `'text'`
  — чистый новый builtin html и уже смигрированный через Save override оба
  пропускают конвертацию, без двойной обёртки. Конвертация происходит
  только для ОТОБРАЖЕНИЯ в RTE, ничего не пишется в CWDB, пока `save()` не
  зафиксирует `format:'html'` в patch явно для этих трёх id — именно этот
  момент необратимо коммитит миграцию. Restore original по-прежнему
  корректно возвращает настоящий builtin html.
- Побочная находка при этом: вкладка «Страницы» проверяется теперь и на
  реальное наличие `tpl.pages`, не только на `isHtml()` — иначе три
  мигрируемых шаблона получили бы пустую вкладку, которой у них никогда не
  было (в отличие от `sys.visit.*.letter`, где memo-страница — часть
  builtin).

**Проверено реальным WebKit-рендерером** (не только логической
симуляцией): полный сценарий старый text-override → RTE → bold → save →
reopen → форматирование и токены целы, без двойной конверсии; чистый новый
builtin без двойного `<p>`; toкен `{congregation}` внутри жирного текста
корректно подставляется в preview; mobile viewport (390px) — вкладки,
тулбар, меню «Вставка» и языковое меню не ломают layout.

i18n: 1 новый ключ (`doc.lang_new`), все 5 языков — долг перевода = 0.

Split-view, breakpoint 1201, draggable picker, caret-fix, поиск/список
picker'а, multiple insertion, template token engine, `shared/templates.js`
— не тронуты.

## 2026-09-02 (пятый заход) — Документы: «Восстановить оригинал» больше не оставляет пустой редактор

**Версии:** Документы `1.9.1 → 1.9.2` (патч — исправление подтверждённого
дефекта). Version-only патч-бамп (правка `shared/version.js` требует его у
cache-first оболочек, подтверждено `check-shared-bump.mjs` с
`CW_BUMP_BASE=HEAD`): хаб `0.41.12 → 0.41.13`, Конгрессы `4.46.34 → 4.46.35`,
Школа пионеров `1.14.12 → 1.14.13`, Назначения `5.5.51 → 5.5.52`. Клиндарий
не в списке — stale-while-revalidate, бамп не требуется.

Диагностика (по запросу Алекса, без слепой правки) точно нашла причину:
`resetToOriginal()` вызывал `CWTemplates.reset(id)`, который корректно
удаляет пользовательскую запись — но набор языков у builtin часто **уже**,
чем у удалённой пользовательской версии (например, `sys.visit.congregation.
email` в реестре существует только на `ru`, а пользователь мог вручную
сохранить перевод на `uk`). `state.lang` при этом не пересчитывался: после
reset он оставался на уже несуществующей колонке, `columnBody(tpl,
state.lang)` молча возвращала пустую строку, и редактор выглядел так, будто
Restore original стёр текст — хотя реальный builtin-текст оставался целым,
просто не на той вкладке языка.

Fix в `resetToOriginal()`: после `reset()` список `Object.keys(fresh.
translations || {})` проверяется на присутствие текущего `state.lang` — тот
же принцип fallback, что уже в `openEditor()` (остаться на текущем языке,
если он всё ещё доступен, иначе переключиться на первый доступный язык
нового набора), затем `renderLangs()`/`loadColumn()` как раньше.
`CWTemplates.reset()`/формат хранилища не менялись — правка только в
`documents/js/app.js`.

RTE-логика (Ж/К/Ч) и language selector (chip «UK»/«RU» и т.п.) — намеренно
не тронуты в этой фазе, по отдельному решению Алекса ждут своих следующих
фаз.

## 2026-09-02 (второй заход) — Документы: variable picker перетаскивается на desktop

**Версии:** Документы `1.7.2 → 1.8.0` (minor — новый функционал). Version-only
патч-бамп (правка `shared/version.js` требует его у cache-first оболочек,
подтверждено `check-shared-bump.mjs` с `CW_BUMP_BASE=HEAD`): хаб
`0.41.9 → 0.41.10`, Конгрессы `4.46.31 → 4.46.32`, Школа пионеров
`1.14.9 → 1.14.10`, Назначения `5.5.48 → 5.5.49`. Клиндарий не в списке —
stale-while-revalidate, бамп не требуется.

Селектор переменных на desktop теперь открывается справа над preview-зоной
(редактор слева остаётся максимально открытым) и может быть перетащен
мышкой/Pointer Events за шапку «Переменные» в любое удобное место экрана.

- **Позиционирование.** Нативный `<dialog>` остаётся модальным через
  `showModal()` без изменений — desktop-режим (`≥1201px`, тот же порог, что
  уже определяет wide для split-view) снимает браузерное центрирование
  (`margin:0`) и держит `left`/`top` через JS
  (`computeDefaultVarsDialogPos()`/`applyVarsDialogPos()` в
  `documents/js/app.js`). Дефолтная позиция вычисляется от фактической
  ширины диалога и текущего `window.innerWidth`, не хардкодом.
- **Drag.** `pointerdown`/`pointermove`/`pointerup` с `setPointerCapture()`
  на `.vars-dialog__head`; клик по кнопке закрытия (`e.target.closest
  ('button')`) не инициирует drag; поиск/список физически вне шапки, туда
  pointerdown не долетает вовсе. `cursor: grab`/`grabbing` — визуальная
  подсказка.
- **Последняя позиция сессии.** `varsDialogPos` — простая переменная в
  замыкании (не персистится между перезагрузками страницы, по утверждённому
  плану — не требуется на этой фазе). `null`, пока пользователь не двигал
  диалог; после `pointerup` хранит последнюю зажатую в границы позицию.
  Следующее открытие использует её вместо дефолтной.
- **Clamp.** Общая `clampVarsDialogPos()` не даёт окну уехать полностью за
  viewport (минимум 80px шапки остаётся видимым с любой стороны) —
  переиспользуется и на `pointerup`, и на `resize`, и на пересечении
  wide/mobile порога.
- **Mobile не тронут.** `isWide()` проверяется заново на каждый
  `pointerdown`, а не один раз при навеске — переход wide→mobile во время
  открытого диалога не оставляет «залипший» обработчик. При пересечении
  порога в mobile-сторону inline `left`/`top` явно очищаются
  (`dlg.style.left = ''`) — иначе их специфичность перебила бы CSS
  bottom-sheet раскладку целиком. `varsDialogPos` при этом не обнуляется —
  при возврате на wide последняя позиция восстанавливается.

Split-view, пропорции колонок, breakpoint 1201, preview rendering,
caret-fix, поиск/список picker'а, multiple insertion, variable mappings,
i18n, template engine — не тронуты. HTML не менялся вовсе: существующая
разметка `.vars-dialog__head`/`#varsDialogClose` оказалась пригодна как
drag-handle без изменений.

## 2026-09-02 — Документы: кнопка переменной и перекрытие picker — реальные CSS-причины найдены и исправлены

**Версии:** Документы `1.7.1 → 1.7.2` (патч — исправление дефекта). Version-only
патч-бамп (правка `shared/version.js` требует его у cache-first оболочек,
подтверждено `check-shared-bump.mjs` с `CW_BUMP_BASE=HEAD`): хаб
`0.41.8 → 0.41.9`, Конгрессы `4.46.30 → 4.46.31`, Школа пионеров
`1.14.8 → 1.14.9`, Назначения `5.5.47 → 5.5.48`. Клиндарий не в списке —
stale-while-revalidate, бамп не требуется.

Прошлая правка (восьмой заход, 01.09.2026) поменяла JS-логику
(`view === 'edit'` вместо `viewEdit.hidden`), но реальный браузерный тест
показал: оба дефекта остались. Диагностика по требованию Алекса —
«сначала не правь код» — показала, что JS был верен с самого начала, оба
бага были чисто CSS-каскадными и не проявлялись ни в изолированной
JS-симуляции (jsdom), ни в статичном скриншоте без взаимодействия.

- **Кнопка «+ Вставить переменную» оставалась видимой на Preview.**
  `setView()` действительно ставил `insertVarBtn.hidden = true` — но
  `.md-btn { display: inline-flex }` (`shared/style.css`) — авторское
  CSS-правило, побеждающее браузерный UA-стиль `[hidden]{display:none}` в
  каскаде независимо от совпадающей специфичности внутри origin (тот же
  класс бага, что раньше был у `.vars-dialog`). Подтверждено реальным
  WebKit-рендерером на изолированном тесте: jsdom дал ложноотрицательный
  результат, его модель специфичности не воспроизводит этот пограничный
  случай браузеров. Fix — локально в Documents (осознанно не расширяя scope
  на `shared/style.css` ради одной кнопки):
  `#insertVarBtn[hidden] { display: none; }`.
- **Карточки picker заезжали под поле поиска.** Первая гипотеза (нет
  непрозрачного фона на шапке) оказалась неполной: добавление `background` +
  `z-index` не устранило баг при повторной проверке тем же WebKit-тестом.
  Настоящая причина — отсутствие `flex-shrink: 0` на `.vars-dialog__head`/
  `.vars-dialog__search`: при ограниченной `max-height` у диалога (обычный
  случай — переменных много) браузер сжимает любой flex-item со свободным
  `flex-shrink` по умолчанию, и шапка/поиск теряли часть визуальной высоты
  вместо того, чтобы остаться нетронутыми, пока сжимается только список.

**Версии:** Клиндарий `9.93.0 → 9.94.3`. Остальные модули не затронуты.

Уточнение предыдущей правки той же карточки: визуально высокая и пустая на
mobile, плюс «Нужно отправить» появлялось даже когда по рабочему правилу
письмо ещё рано отправлять.

- **Root cause высокой пустой карточки — исправлен через layout, не
  замаскирован фиксированной высотой.** `.nv-row` держал
  `align-items:stretch`, из-за чего компактная карточка растягивалась под
  высоту соседней «Следующее посещение» (там контента больше — тип
  посещения, диапазон дат, два флага). Заменено на `align-items:flex-start`
  на контейнере + явный `align-self:stretch` только на `#nextVisitPill` —
  основная карточка не потеряла высоту, компактная считает её от своего
  содержимого.
- **Порог 60 дней до начала посещения** (по дате начала, не окончания —
  та же формула `daysUntil`, что и в `App.data.getUpcomingReminders()`, не
  отдельная копия): `> 60` дней — зелёный индикатор, «Ещё рано · До
  отправки N дня»; `≤ 60` — красный индикатор, «Пора отправить письмо».

  использованы существующие токены `--status-success`/`--status-critical`

  persisted-флага — чисто вычисляемое UI-правило поверх `entry.flags.letter`.
  Состояния `partial`/`full` остались зелёными и без порога — это спокойные
  success-состояния, не про срочность конкретного письма.
- **Mobile:** компактный status-block по содержимому, без больших пустых
  областей; длинное название переносится, статус-строка и стрелка не рвут
  layout, горизонтального скролла нет. Desktop: обе карточки по-прежнему в
  ряд, вторая — компактнее основной.
- **Второй заход по mobile-высоте (9.94.1), после реальной проверки на
  телефоне.** Первое исправление root cause (`align-items:stretch →
  flex-start` на `.nv-row`) оказалось верным, но неполным — огромная пустая
  область под компактной карточкой сохранялась. Настоящая причина: `.nv-row`
  переключается на `flex-direction:column` на mobile, а вместе с этим
  меняется смысл `flex-grow` у детей — то же самое число, что на desktop
  растягивало карточки по ширине, на mobile растягивало их по высоте,
  заставляя обе карточки делить свободное вертикальное пространство
  контейнера поровну вне зависимости от объёма контента. Исправлено явным
  `flex:0 0 auto` на `#nextVisitPill` и `#letterDuePill` только внутри
  `@media (max-width:767px)` — desktop-правила не тронуты.
- **Третий заход, ширина letterDuePill на mobile (9.94.2), после
  подтверждения root cause высоты живым скриншотом с телефона.** Высота уже
  была верной, но карточка визуально оказывалась у́же соседней «Следующее
  посещение» — обе стороны совпадали не полностью. Причина: в
  `flex-direction:column` шириной (кросс-осью) управляет `align-items`, а не
  `flex-grow`; базовое `align-items:flex-start` на `.nv-row` не
  переопределялось на mobile, поэтому каждый ребёнок брал ширину по
  собственному содержимому — у более насыщенной `#nextVisitPill` она и так
  была близка к полной, у компактной `#letterDuePill` — меньше. Добавлен
  один `align-self:stretch` только на `#letterDuePill` внутри того же
  media query; `flex:0 0 auto` (высота) не тронут — `align-self` в
  column-контейнере влияет только на кросс-ось (ширину), не на главную
  (высоту).
- **Четвёртый заход (9.94.3), системная Grid-переработка после проверки на
  нескольких реальных desktop/tablet ширинах.** Три предыдущих захода чинили
  высоту и ширину точечными flex-хаками — по отдельности верными, но вместе
  оставлявшими раскладку "плавающей": на tablet/wide-desktop пара карточек
  имела фиксированный `max-width:760px` и превращалась в два маленьких
  острова с пустым пространством справа вместо использования реальной
  ширины календарной колонки. `.nv-row` переведён с flex на CSS Grid:
  `grid-template-columns: minmax(0,1.6fr) minmax(280px,1fr)` на `>767px`
  (пропорция ~60–65%/35–40%, без верхнего потолка ширины), `1fr` на
  `≤767px` (mobile — без изменений). `align-items:start` на Grid — это
  прямой аналог прежнего `align-items:flex-start`, без него Grid по
  умолчанию растягивает ячейки строки и высота снова "поплыла" бы, уже
  через Grid, а не через flex-grow. Все точечные flex/max-width/align-self
  правила на `.nv-row` и её детях убраны как избыточные.
- **Уточнение той же правки: `.nv-row` не равен левой колонке календаря.**
