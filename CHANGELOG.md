## 2026-09-02 (десятый заход) — Документы: языковое меню больше не уезжает за экран, Restore/Save на одной линии

**Версии:** Документы `1.10.3 → 1.10.4` (патч — два визуальных исправления,
не новый функционал). `shared/*` в этой фазе не менялся — версии остальных
модулей не пересчитывались заново.

Реальный тест v1.10.3 показал два визуальных дефекта, оба чисто CSS,
`documents/js/app.js` не тронут вовсе — подтверждено побайтовым сравнением
с прошлой доставкой.

- **Панель языкового меню уезжала за левый край экрана.** `.md-menu__panel`
  (`shared/style.css`) по умолчанию `right:0` — растёт влево от правого
  края триггера, что верно для меню в конце строки (например, «Вставка» в
  тулбаре). Но `#edLangMenu` стоит отдельным блоком у левого края страницы,
  и рост влево от узкой кнопки «UK ▾» уводил панель ~150px за границу
  viewport — видна была только тонкая полоска, все пункты UK/RU/DE/PL/EN
  недоступны. Fix локален: `#edLangMenuPanel { left: 0; right: auto; }` —
  `shared/style.css` и меню «Вставка» не тронуты. Подтверждено реальным
  WebKit-рендерером на desktop и mobile (390px) — все 5 языков полностью
  видны в обоих случаях, без horizontal overflow.
- **«Восстановить оригинал» и «Сохранить» не были на одной линии.** После
  переноса save-статуса под кнопку (прошлая фаза, B1) `.ed__save-group`
  (кнопка + статус + gap) стала выше простой кнопки `#resetBtn` —
  `.ed__head { align-items: center }` центрировал `#resetBtn` по этой
  увеличенной высоте строки, визуально сдвигая его ниже верхнего края
  «Сохранить». Fix точечный: `#resetBtn` и `.ed__save-group` получили
  `align-self: flex-start` — выравниваются по верхнему краю строки, не
  трогая `align-items` самого `.ed__head` и поведение остальных элементов.
  Подтверждено реальным WebKit-рендерером: обе кнопки на одной линии на
  desktop; mobile wrap-поведение (перенос «Сохранить» на новую строку при
  недостатке ширины) сохранено без изменений.

i18n: новых ключей не потребовалось, 119 ключей без изменений, долг
перевода = 0.

RTE, 5 языков, lazy migration, Restore per-language, preview, variable
picker, Insert menu, взаимное закрытие меню — не тронуты (JS не менялся
в этой фазе).

## 2026-09-02 (девятый заход) — Документы: статус сохранения переехал к кнопке «Сохранить»

**Версии:** Документы `1.10.2 → 1.10.3` (патч — UX-улучшение по утверждённой
визуализации, не новый функционал). `shared/*` в этой фазе не менялся —
версии остальных модулей не пересчитывались заново.

Финальный UX-аудит (пункт B1) нашёл: статус сохранения жил в шапке хаба,
рядом с номером версии модуля, далеко от кнопки «Сохранить» — пользователь
не видел результат действия в поле зрения самого действия.

- **Новый `#editorSaveStatus`** — тот же переиспользуемый shared-компонент
  `.md-savestatus` (`shared/style.css`, раздел 5.11 — уже используется
  Конгрессами и Назначениями в topbar), второй экземпляр внутри
  `.ed__head`, в `.ed__save-group` рядом с `#saveBtn`. Новый визуальный
  примитив не создавался.
- **Старый `#saveStatus` в topbar остался** — он обслуживает несвязанные
  состояния (копирование записи в Архиве, ошибка создания шаблона для
  типа задания Конгрессов — происходит до открытия редактора вовсе) и не
  является тем же состоянием, что save-status редактора: перемещать его
  целиком значило бы потерять эти сообщения на экранах без открытого
  редактора.
- **Новая `editorStatus(key, dataState)`** отделена от существующей
  `status(key)` — один источник истины для dirty/saving/saved/error
  редактора, другой для всего остального. `dataState` включает уже
  существовавший, но не работавший CSS `.md-savestatus[data-state="..."]`
  (цветной индикатор был определён в shared-слое с самого начала, JS
  никогда не выставлял атрибут).
- **`#edBadge` (системный/изменён) не смешан с save-status** — это
  происхождение записи (override или нет), состояние dirty/saved —
  совсем другое, оба остаются раздельными индикаторами.
- Добавлен `aria-live="polite"` — отсутствовал у статуса вовсе.
  `editorStatus(null, null)` очищает статус при открытии нового шаблона,
  чтобы не показывать состояние от предыдущего открытого документа.

**Подтверждено реальным WebKit-рендерером:** все 4 состояния
(dirty/saving/saved/error) с корректными цветными индикаторами; desktop —
статус виден точно под кнопкой «Сохранить»; mobile 390px — самый длинный
текст («Есть несохранённые изменения») переносится без horizontal
overflow, ширина рендера подтверждена точно равной viewport (390px),
Save/Restore остаются доступны, ничего не перекрывается.

i18n: новых ключей не потребовалось — все 5 нужных ключей уже существовали
на всех 5 языках, долг перевода = 0.

RTE, language selector, Restore-логика, меню, variable picker, preview,
pages, экран библиотеки — не тронуты.

## 2026-09-02 (седьмой заход) — Документы: «Восстановить оригинал» относится только к текущему языку

**Версии:** Документы `1.10.0 → 1.10.1` (патч — исправление UX-проблемы, не
новый функционал). `shared/*` в этой фазе не менялся — версии остальных
модулей не пересчитывались заново, каскад из прошлой фазы (builtin.js) уже
актуален и подтверждён.

Реальный тест v1.10.0 показал: пользователь на UK нажимал «Восстановить
оригинал», редактор молча переключался на RU (потому что builtin существует
только на RU), а колонка UK становилась пустой при повторном выборе.
Технически данные не терялись, но кнопка вела себя не так, как названа —
удаляла override всех языков разом ради восстановления одного.

- **`resetToOriginal()` больше не вызывает `CWTemplates.reset(id)`** —
  он удаляет пользовательскую запись целиком, все языки сразу.
  `shared/templates.js` не менялся: переиспользован уже существующий
  `CWTemplates.save(id, lang, patch)`, который и так переписывает только
  `translations[lang]`, оставляя остальные ключи объекта как есть.
- **Если builtin содержит текущий язык** — восстанавливается только он,
  через `save()` с телом из builtin; остальные языки, если пользователь их
  редактировал, не трогаются вовсе; редактор остаётся на текущем языке.
- **Если builtin не содержит текущий язык** — ничего не удаляется и не
  сохраняется. Показывается понятное сообщение с названием обоих языков и
  явным выбором: перейти на язык, где оригинал есть, или отменить. Раньше
  переключение происходило молча.
- Новый локальный `builtinTpl(id)` в `documents/js/app.js` читает
  `self.CW_BUILTIN_TEMPLATES` напрямую (та же глобальная переменная, что уже
  использует приватная `builtinById()` внутри `shared/templates.js`) — не
  потребовалось добавлять новый публичный метод в shared-слой ради одной
  функции одного модуля.
- Верхний `#docLang` (глобальный, персистентный «предпочтительный язык
  документа для следующего открытия») переименован на всех 5 языках для
  ясности — функционально не изменился: «Язык документа» → «Язык документа
  по умолчанию» (и аналоги на UK/EN/PL/DE). Названия карточек в библиотеке
  по-прежнему не зависят от него — это ожидаемое поведение, они следуют
  языку интерфейса.

i18n: 1 новый ключ (`doc.restore_lang_missing`) + обновлён текст
`doc.doclang_label`, все 5 языков — долг перевода = 0.

RTE, execCommand, lazy migration, five-language editor selector, variable
picker, draggable dialog, меню «Вставка», split-view — не тронуты.

## 2026-09-02 (шестой заход) — Документы: полноценный выбор языка документа и rich text для сопроводительных писем

**Версии:** Документы `1.9.2 → 1.10.0` (minor — новый функционал). Правка
`shared/templates/builtin.js` — это правка общего слоя, патч-бамп подтверждён
явным прогоном `check-shared-bump.mjs` с `CW_BUMP_BASE=HEAD` (не
предполагался): хаб `0.41.13 → 0.41.14`, Конгрессы `4.46.35 → 4.46.36`,
Школа пионеров `1.14.13 → 1.14.14`, Назначения `5.5.52 → 5.5.53`. Клиндарий
не в списке — stale-while-revalidate, подтверждено тем же прогоном.

Две независимые UX-функции, обе доведены до полной реализации после
диагностики без слепого кода.

- **Выбор языка документа.** Плоский chip-набор `#edLangs`, строившийся из
  `Object.keys(tpl.translations)`, заменён на выпадающее меню (`.md-menu`,
  тот же примитив, что уже использует меню «Вставка») с фиксированным
  списком всех пяти языков проекта — порядок `UK/RU/DE/PL/EN`. Раньше при
  одной колонке (например, только RU у builtin) пользователь видел
  единственный вариант и не мог создать перевод на другой язык вовсе.
  `CWTemplates.save()` (`shared/templates.js`) уже мёржил новый язык в
  `translations` без удаления остальных — этого оказалось достаточно,
  правка полностью в `documents/js/app.js`/`documents/index.html`. Выбор
  ещё не существующего языка просто переключает `state.lang`; реальная
  запись появляется только по явному Save. Меню различает «перевода нет»
  (колонка существует, но пуста) от «новый перевод» (колонки ещё нет)
  текстом подписи пункта — без нового сложного UI. Это язык документа, не
  язык интерфейса — не связан с `CWDocLang`/`CWI18n`.
- **Rich text для трёх email-body шаблонов** (`sys.visit.congregation.email`,
  `.group.email`, `.pregroup.email`) — единственные три id, переведённые
  `format:'text' → 'html'` в `shared/templates/builtin.js`. Все остальные
  text-шаблоны (salutation, конгрессы, школа) не тронуты.
  `execCommand('bold'/'italic'/'underline')` подтверждён рабочим реальным
  WebKit-рендерером (программная Selection/Range + execCommand,
  `success:true`, реальный `<b>`/`<i>` в результате) — не переписывался.
- **Lazy migration, не destructive.** `shared/templates.js`/`effective()` не
  тронуты — решение целиком локально в Documents. Новый
  `RTE_MIGRATION_IDS` принудительно считает `isHtml()===true` для этих трёх
  id независимо от сырого `tpl.format` (который у существующих
  пользовательских override мог остаться `'text'` от старой версии builtin).
  `needsLazyHtmlMigration()` — точная развилка: конвертировать через уже
  существующий `plainToHtml()` нужно только когда сырой формат ещё `'text'`
  — чистый новый builtin html и уже смигрированный через Save override оба
  пропускают конвертацию, без двойной обёртки. Конвертация происходит
  только для ОТОБРАЖЕНИЯ в RTE, ничего не пишется в CWDB, пока `save()` не
  зафиксирует `format:'html'` в patch явно для этих трёх id — именно этот
  момент необратимо коммитит миграцию. Restore original по-прежнему
  корректно возвращает настоящий builtin html.
- Побочная находка при этом: вкладка «Страницы» проверяется теперь и на
  реальное наличие `tpl.pages`, не только на `isHtml()` — иначе три
  мигрируемых шаблона получили бы пустую вкладку, которой у них никогда не
  было (в отличие от `sys.visit.*.letter`, где memo-страница — часть
  builtin).

**Проверено реальным WebKit-рендерером** (не только логической
симуляцией): полный сценарий старый text-override → RTE → bold → save →
reopen → форматирование и токены целы, без двойной конверсии; чистый новый
builtin без двойного `<p>`; toкен `{congregation}` внутри жирного текста
корректно подставляется в preview; mobile viewport (390px) — вкладки,
тулбар, меню «Вставка» и языковое меню не ломают layout.

i18n: 1 новый ключ (`doc.lang_new`), все 5 языков — долг перевода = 0.

Split-view, breakpoint 1201, draggable picker, caret-fix, поиск/список
picker'а, multiple insertion, template token engine, `shared/templates.js`
— не тронуты.

## 2026-09-02 (пятый заход) — Документы: «Восстановить оригинал» больше не оставляет пустой редактор

**Версии:** Документы `1.9.1 → 1.9.2` (патч — исправление подтверждённого
дефекта). Version-only патч-бамп (правка `shared/version.js` требует его у
cache-first оболочек, подтверждено `check-shared-bump.mjs` с
`CW_BUMP_BASE=HEAD`): хаб `0.41.12 → 0.41.13`, Конгрессы `4.46.34 → 4.46.35`,
Школа пионеров `1.14.12 → 1.14.13`, Назначения `5.5.51 → 5.5.52`. Клиндарий
не в списке — stale-while-revalidate, бамп не требуется.

Диагностика (по запросу Алекса, без слепой правки) точно нашла причину:
`resetToOriginal()` вызывал `CWTemplates.reset(id)`, который корректно
удаляет пользовательскую запись — но набор языков у builtin часто **уже**,
чем у удалённой пользовательской версии (например, `sys.visit.congregation.
email` в реестре существует только на `ru`, а пользователь мог вручную
сохранить перевод на `uk`). `state.lang` при этом не пересчитывался: после
reset он оставался на уже несуществующей колонке, `columnBody(tpl,
state.lang)` молча возвращала пустую строку, и редактор выглядел так, будто
Restore original стёр текст — хотя реальный builtin-текст оставался целым,
просто не на той вкладке языка.

Fix в `resetToOriginal()`: после `reset()` список `Object.keys(fresh.
translations || {})` проверяется на присутствие текущего `state.lang` — тот
же принцип fallback, что уже в `openEditor()` (остаться на текущем языке,
если он всё ещё доступен, иначе переключиться на первый доступный язык
нового набора), затем `renderLangs()`/`loadColumn()` как раньше.
`CWTemplates.reset()`/формат хранилища не менялись — правка только в
`documents/js/app.js`.

RTE-логика (Ж/К/Ч) и language selector (chip «UK»/«RU» и т.п.) — намеренно
не тронуты в этой фазе, по отдельному решению Алекса ждут своих следующих
фаз.

**Версии:** Документы `1.7.1 → 1.7.2` (патч — исправление дефекта). Version-only

stale-while-revalidate, бамп не требуется.

Прошлая правка (восьмой заход, 01.09.2026) поменяла JS-логику
(`view === 'edit'` вместо `viewEdit.hidden`), но реальный браузерный тест
показал: оба дефекта остались. Диагностика по требованию Алекса —
«сначала не правь код» — показала, что JS был верен с самого начала, оба
бага были чисто CSS-каскадными и не проявлялись ни в изолированной
JS-симуляции (jsdom), ни в статичном скриншоте без взаимодействия.

- **Кнопка «+ Вставить переменную» оставалась видимой на Preview.**
  `setView()` действительно ставил `insertVarBtn.hidden = true` — но
  `.md-btn { display: inline-flex }` (`shared/style.css`) — авторское
  CSS-правило, побеждающее браузерный UA-стиль `[hidden]{display:none}` в
  каскаде независимо от совпадающей специфичности внутри origin (тот же
  класс бага, что раньше был у `.vars-dialog`). Подтверждено реальным

  результат, его модель специфичности не воспроизводит этот пограничный
  случай браузеров. Fix — локально в Documents (осознанно не расширяя scope

  непрозрачного фона на шапке) оказалась неполной: добавление `background` +
  `z-index` не устранило баг при повторной проверке тем же WebKit-тестом.
  Настоящая причина — отсутствие `flex-shrink: 0` на `.vars-dialog__head`/
  `.vars-dialog__search`: при ограниченной `max-height` у диалога (обычный
  случай — переменных много) браузер сжимает любой flex-item со свободным

  вместо того, чтобы остаться нетронутыми, пока сжимается только список.

  единственным `overflow-y: auto`, ничего в scroll-структуре не менялось.
  Background на шапке оставлен как дополнительная защита.
