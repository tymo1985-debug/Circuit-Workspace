# Общий слой документов — архитектурное предложение

*Статус: принято Алексом 11.08.2026. Фаза 1 внедрена 12.08.2026 (см. раздел 16).*
*База анализа: коммит `18bfff1`, хаб 0.18.4, Конгрессы 4.30.0, Клиндарий 9.66.1,*
*Школа пионеров 1.10.0, Назначения 5.4.0.*
*Развёрнутая таблица находок — в `01-audit.md`.*

---

## 1. Задача

Тексты писем сейчас живут внутри модулей, а часть — прямо в их настройках.
Вопрос Алекса: вынести работу с письмами, документами и формулярами в отдельный
общий модуль. Ниже — анализ, три варианта архитектуры, выбранный вариант и план
внедрения.

---

## 2. Что нашлось в коде

В проекте **три независимых механизма документов**, которые не знают друг о друге.

| # | Механизм | Где | Синтаксис переменных | Кто правит текст |
|---|---|---|---|---|
| A | Свободный текст + плейсхолдеры | `congress-project/js/letters.js:10` → `settings.templates[lang]`, `settings.templatesByType[type]` | `{{senderName}}` — 21 плоское имя (`PH`, строка 11) | пользователь, редактор `js/template-editor.js` |
| B | HTML из RTE + плейсхолдеры | `circuit-planner/app.js:84–133` → `settings.letterTemplate*`, `letterPages*`, `emailBody*`, `letterSalutation*`, `memoTemplate` | `{congregation}` — одинарные скобки, 8 имён (`substitutePlaceholders`, строка 2870) | пользователь, RTE в настройках |
| C | Фиксированная разметка + словарь | `appointments/index.html` + `doc.ap.*`; `pioneer-school/i18n/doc.js` (~145 ключей `doc.ps.*`) | `{name}` через `CWI18n.t()` | **никто из пользователей** — только носитель языка |

Главный вывод аудита, который меняет постановку задачи:

> **Не всё, что выглядит как письмо, является шаблоном.**

Письмо «Назначений» и анкета Школы — не пользовательские шаблоны, а официальные
документы с выверенной формулировкой. Их корректность держится на том, что текст
лежит в словаре и переводится носителем языка (правило зафиксировано в
`AGENTS.md` и в шапке `pioneer-school/i18n/doc.js`). Сделав их редактируемыми
шаблонами, мы:

- сломаем пайплайн вычитки — переводчик правит одну колонку словаря, а не копии
  в браузерах пользователей;
- дадим возможность случайно испортить документ, который уходит в собрание;
- потеряем fallback `CWI18n` (пустой перевод → русский текст, документ остаётся
  читаемым, а не превращается в набор ключей).

Поэтому граница проходит не по «письмо / не письмо», а так:

**Общий слой документов владеет текстом, который принадлежит пользователю.
`i18n` владеет текстом, который принадлежит документу.**

## 3. Что ломает нынешнее хранение

Найдено в коде, не предположения.

1. **`ru` и `de` шаблоны Конгрессов — байт-в-байт копии украинского.** Проверено
   на `18bfff1`: три строки по 1592 символа, полное совпадение. Переключатель
   языка механически работает, перевода нет; любая правка формулировки требует
   трёх правок.
2. **Плейсхолдеры несовместимы между модулями.** `{{senderName}}` против
   `{sender}`. Навык, полученный в Конгрессах, не переносится в Клиндарий. Общего
   справочника переменных нет: в Конгрессах это массив `PH`, в Клиндарии —
   отдельная функция `renderPlaceholderReference()`.
3. **Проза лежит в настройках модуля.** `DEFAULT_LETTER_TEMPLATE` +
   `DEFAULT_MEMO_TEMPLATE` — около 9 КБ текста прямо в `circuit-planner/app.js`,
   плюс копия каждого в `localStorage` пользователя × 3 типа визита. Настройки
   превратились в CMS: пять семейств ключей (`letterTemplate*`, `letterPages*`,
   `emailBody*`, `letterSalutation*`, `memoTemplate`).
4. **Бэкап настроек = бэкап документов.** Экспорт настроек Клиндария тащит с
   собой все письма, импорт их перетирает. Пользователь, восстанавливающий цвет
   акцента, теряет отредактированный шаблон.
5. **Истории нет.** В Клиндарии она есть частично: `entry.emailBody` и
   `entry.subject` сохраняются на записи визита — snapshot уже неявно
   реализован. В Конгрессах нет: `letterHTML()` рендерит из текущего шаблона
   каждый раз. Изменил шаблон в октябре — письмо, отправленное в августе,
   выглядит иначе. При печати «всех писем» задним числом это неверная бумага.
6. **Четвёртый механизм на подходе.** Писем в Школе пионеров нет вовсе
   (проверено). Как только они появятся, при нынешней архитектуре появится и
   четвёртый диалект.

Тезис «Settings хранят поведение, а не прозу» принимается. Уточнение:
`emailMethod`, `owaUrl`, `font`, `fontSize` остаются в Settings — это
действительно поведение.

## 4. Три архитектуры

### A. Central Documents Module

Всё — шаблоны, документы, формуляры — в отдельном модуле `documents/`.

- **+** один экран, где видно всё; сквозной поиск.
- **+** одна модель данных, один редактор, один справочник переменных.
- **−** ради простого письма пользователь уходит из карточки визита в другой
  модуль и возвращается — ровно тот сценарий «из десяти действий», которого
  Алекс не хочет.
- **−** соблазн затащить в Documents данные: «раз он знает имя собрания, пусть
  собрания и хранит».
- **−** новый модуль = новый SW, manifest, иконки, +1 к чек-листу выпуска.

### B. Shared Template Engine

Только `shared/templates.js`: движок подстановки, хранилище, API. Своего UI нет,
каждый модуль редактирует шаблоны у себя, как сейчас.

- **+** минимальное изменение, риск близок к нулю; ложится на паттерн
  `shared/sender.js`, уже доказавший себя.
- **+** снимает диалекты плейсхолдеров и дублирование текстов сразу.
- **−** нет места, где видно все шаблоны: письмо визита по-прежнему ищется в
  настройках Клиндария.
- **−** некуда класть snapshot — каждый модуль изобретёт своё (Клиндарий уже).
- **−** редактор шаблона дублируется в каждом модуле: сейчас их два, станет четыре.

### C. Hybrid

`shared/templates.js` — движок, хранилище и API. `documents/` — тонкий UI поверх
общего хранилища: библиотека, редактор, история. Модули получают контекстные
функции («Создать документ») прямо у себя, не уходя в Documents.

- **+** редактор шаблона существует в одном экземпляре;
- **+** данные остаются в доменных модулях, Documents хранит только шаблоны и
  snapshot'ы;
- **+** типичный сценарий не покидает контекст;
- **−** больше кода, чем в B; две фазы вместо одной.

## 5. Решение: гибрид (C) с двумя поправками

**Поправка 1 — область сужается.** Documents владеет только пользовательскими
шаблонами: письма Конгрессов, письмо/памятка/тело письма Клиндария, будущие
письма Школы. Письмо «Назначений», анкета Школы, S-302, S-253 остаются в `i18n`
(обоснование — раздел 2).

**Поправка 2 — порядок обратный интуитивному.** Сначала `shared/templates.js`
(то есть вариант B целиком), и только потом модуль `documents/`. Причина не в
осторожности: **B — подмножество C**, и работающий B уже даёт основную пользу —
убивает три диалекта плейсхолдеров, выносит прозу из настроек, даёт единый
справочник переменных. Если после B выяснится, что отдельный экран не нужен, на
него не потрачено ничего.

**Почему не A.** В проекте уже есть эталон удачной общей сущности —
`shared/sender.js`. У него нет своего UI, и это правильно: данные отправителя
правятся там, где нужны. Documents отличается тем, что шаблонов много и их надо
перебирать — вот для этого экран и нужен. Но экран — следствие, а не отправная
точка.

**Почему это ложится на нынешнюю архитектуру.** Три предпосылки уже готовы:

- `shared/doclang.js` — язык документа отдельно от интерфейса, работает;
- `shared/sender.js` — namespace `sender.*` фактически существует, вместе с
  готовым рецептом миграции `adopt()`;
- `shared/db.js` — store `communities` спроектирован под будущий справочник
  собраний, откуда возьмётся `congregation.*`.

## 6. Схема

```
   ДОМЕННЫЕ ДАННЫЕ                    ДОКУМЕНТЫ
   (владеют модули)                   (владеет общий слой)

┌──────────────────┐
│ Конгрессы        │  контекст + данные
│  congresses,     │─────────────┐
│  tasks           │             │
├──────────────────┤             │
│ Клиндарий        │             ▼
│  events, entries │──────▶ ┌─────────────────────┐
├──────────────────┤        │ shared/templates.js │
│ Школа пионеров   │──────▶ │   CWTemplates       │
│  students        │        ├─────────────────────┤
├──────────────────┤        │ list(context, lang) │
│ Назначения       │  ✗ НЕ  │ render(id, data)    │
│  (i18n-документ) │  идёт  │ snapshot(doc, ref)  │
└──────────────────┘        └──────────┬──────────┘
      ┌──────────────────┐             │
      │ shared/sender.js │─ sender.* ─▶│
      │ shared/doclang.js│─ язык ─────▶│
      │ shared/db.js     │◀── templates, documents
      └──────────────────┘             │
                                       ▼
                            ┌─────────────────────┐
                            │  documents/         │
                            │  библиотека,        │
                            │  редактор, история  │
                            └─────────────────────┘
```

Стрелки от модулей идут **в** `CWTemplates`, но не обратно. Documents не знает
`entry`, `task`, `student` — модуль сам приводит свои данные к нормализованному
объекту.

## 7. Модель данных

`shared/db.js` поднимается до `DB_VERSION = 2`, добавляются два store.

### `templates`

```js
{
  id: 'tpl_a7f3',
  context: 'visit.congregation.letter',   // ключ подбора, см. раздел 10
  scope: 'system' | 'user',
  baseId: 'tpl_sys_visit_letter' | null,  // от какого системного произошёл
  format: 'text' | 'html',                // Конгрессы — text, Клиндарий — html
  title: 'Письмо перед визитом к собранию',
  translations: {
    uk: { subject: '…', body: '…' },
    ru: { subject: '',  body: ''  },      // пусто = перевода нет
    de: { … },
  },
  pages: [ { id, title, body } ],         // доп. страницы (памятка Клиндария)
  updatedAt: '2026-08-11T…',
  archived: false
}
```

**Один `templateId` + `translations`, а не отдельные шаблоны на язык.** Три
причины: (1) так уже устроены оба существующих механизма —
`settings.templates[lang]` и словарь `doc.*`, миграция становится тождественной;
(2) fallback превращается в чтение поля, а не в поиск по коллекции; (3)
переводчик получает знакомую задачу «заполни пустую колонку» — ровно как в
`pioneer-school/i18n/doc.js`.

Fallback: запрошенный язык → первый непустой в порядке `langs` модуля → `uk`.
Пустой перевод отдаёт исходный язык и помечается `pending` — как уже сделано
через `PS_DOC_LANGS_READY`.

### `documents` (snapshot'ы)

```js
{
  id: 'doc_9c21',
  templateId: 'tpl_a7f3',
  templateUpdatedAt: '2026-07-02T…',  // версия шаблона на момент генерации
  lang: 'uk',                         // фактически использованный, не запрошенный
  subject: '…',
  body: '…',                          // ГОТОВЫЙ текст, подстановка выполнена
  pages: [ … ],
  ref: { module: 'circuit-planner', entity: 'entry', id: 'entry_31' },
  data: { … },                        // нормализованный вход — для «пересобрать»
  createdAt: '…',
  reason: 'print' | 'send' | 'manual'
}
```

`body` — уже подставленный текст, не шаблон. Именно это гарантирует неизменность
истории.

**Чего в модели нет намеренно:** названий собраний, имён участников, дат визита.
Только `ref` на сущность-владельца и `data` как слепок входа. Второй копии
справочников не создаётся.

## 8. Плейсхолдеры

Единый синтаксис `{{namespace.field}}`, двойные скобки: побеждает диалект
Конгрессов — он строже и не конфликтует с одинарными скобками в живом тексте.

| Namespace | Источник | Поля |
|---|---|---|
| `sender.*` | `shared/sender.js` | `name`, `code`, `address`, `phone1`, `phone2`, `email` |
| `doc.*` | движок | `today`, `lang` |
| `congregation.*` | `CWDB.communities` / модуль | `name`, `number`, `address`, `contactName`, `contactPhone`, `contactEmail` |
| `visit.*` | Клиндарий | `startDate`, `endDate`, `type`, `typeLabel` |
| `congress.*` | Конгрессы | `name`, `theme`, `place`, `date`, `rehearsalDate`, `rehearsalTime`, `recordingDeadline`, `responseDeadline` |
| `assignment.*` | Конгрессы | `number`, `title`, `time`, `type`, `participant`, `recordingMedia`, `recordingKind`, `notes` |
| `student.*`, `school.*` | Школа | зарезервированы |

**Обязательная совместимость.** У пользователей в браузерах лежат
отредактированные шаблоны со старым синтаксисом. Переименование плейсхолдера
молча ломает их письма — самая опасная ошибка этой миграции. Решение: таблица
алиасов в движке, действующая **бессрочно**:

```
{{senderName}}   → sender.name
{{congressDate}} → congress.date
{congregation}   → congregation.name
{start_date}     → visit.startDate
…
```

Плюс однократная нормализация текста при `adopt()` — старые имена переписываются
в новые, чтобы панель переменных показывала актуальный набор. Алиасы при этом
остаются: пользователь мог скопировать старый шаблон из заметок.

**Неизвестный плейсхолдер** не подставляется пустой строкой молча — остаётся в
тексте как есть и подсвечивается в предпросмотре. Пустая строка вместо даты в
готовом письме хуже, чем видимое `{{visit.startDate}}`.

## 9. Языки

Механизм выбора уже существует и работает — `shared/doclang.js`, приоритет
`cw-doclang:<module>` → `cw-doclang` → fallback модуля; язык интерфейса в цепочке
не участвует. Documents просто спрашивает `CWDocLang.get()`.

Добавляется:

- в редакторе — переключатель колонки перевода с пометкой «пусто → показывается uk»;
- на карточке шаблона — индикатор `pending`, если язык документа выбран, а
  перевода нет;
- в snapshot — фактически использованный язык (может отличаться от запрошенного
  из-за fallback), иначе в истории не понять, почему письмо украинское.

**Правило проекта сохраняется:** переводы пишет носитель языка. Claude готовит
структуру и пустые ключи, помечая их явно.

## 10. Системные и пользовательские шаблоны

Модель `System → Duplicate → User` верна, но в Конгрессах уже реализована более
простая и лучшая версия: `resetTemplate()` возвращает системный текст, а до этого
пользователь правит копию прямо на месте. Явного «Duplicate» нет, и он не нужен —
это лишний шаг. Закрепляем именно этот вариант:

```
Системный шаблон (в коде, shared/templates/builtin.js)
        │
        │ пользователь начал править
        ▼
Пользовательская запись в CWDB.templates (scope:'user', baseId → системный)
        │
        │ «Восстановить оригинал»
        ▼
запись удаляется, снова читается системный
```

Следствия:

- обновление приложения обновляет системные тексты у всех, кто их не правил, —
  автоматически;
- у тех, кто правил, ничего не меняется, но карточка помечается «системный
  шаблон обновлён» с возможностью посмотреть дифф;
- «Восстановить оригинал» = удаление записи, а не копирование текста: проще и не
  оставляет мусора.

Системные шаблоны живут в коде (`shared/templates/builtin.js`), а не в базе, —
иначе их нельзя обновить при выпуске.

### Контексты

Контекст — строка `<домен>.<сущность>.<назначение>`:

| Контекст | Модуль |
|---|---|
| `congress.assignment.invitation` | Конгрессы |
| `visit.congregation.letter` / `.group.` / `.pregroup.` | Клиндарий |
| `visit.*.email` | Клиндарий |
| `visit.*.salutation` | Клиндарий |
| `visit.memo` | Клиндарий |
| `school.student.invitation` | Школа (будущее) |

Три отдельных контекста для типов визита, а не поле `visitType` внутри шаблона:
Клиндарий уже так устроен (`letterTemplate` + suffix), и у типов разные тексты, а
не разные подстановки.

## 11. Snapshot'ы

**Автоматически** — только в момент, когда документ покинул приложение: печать,
экспорт PDF, отправка письма. Это точка, после которой бумага существует в
реальном мире и обязана остаться неизменной.

**Не сохранять**: предпросмотр, открытие композера, черновое редактирование —
иначе история захламляется почти одинаковыми записями.

**Черновик** живёт на самой сущности, а не в `documents` — как уже сделано в
Клиндарии (`entry.emailBody`, `entry.subject`). Это правильно и менять не надо:
черновик принадлежит визиту, а не архиву.

**Ручное «Сохранить документ»** — отдельная кнопка в композере, `reason:'manual'`.

**Против накопления:** snapshot — это текст, единицы килобайт; тысяча писем ≈
3–5 МБ в IndexedDB, несопоставимо с уже лежащими там шрифтами. Реальный риск не в
объёме, а в шуме списка, поэтому история группируется по сущности (все документы
визита — под визитом), а не сваливается плоским списком.

## 12. UI/UX

Измеримое требование, которое фиксируется как проектное:

> **Создание типового письма — не более двух действий от карточки сущности до
> предпросмотра.** Решение, которое это нарушает, отклоняется, каким бы стройным
> ни было.

### Главный путь — контекстный, из модуля

```
Prague East · 12–17 жовтня 2026
[ Створити документ ▾ ]
   ├ Лист перед візитом        ← контекст visit.congregation.letter
   ├ Тіло e-mail
   └ Пам'ятка координатору
```

Клик по пункту → сразу предпросмотр с подставленными данными. Выбор шаблона не
является отдельным шагом, если в контексте он один. Язык берётся из `CWDocLang`,
а не спрашивается. Источник данных не выбирается — мы пришли из карточки визита,
он известен. **Итого два клика.**

Дальше — знакомая панель действий: «Копировать тему» · «Копировать текст» ·
«Печать» · «PDF» · «Сохранить». Ровно то, что уже есть в модальном окне письма
Клиндария.

### Экран Documents — второстепенный

```
Документы                                       [ + Шаблон ]

  Поиск…                                        Язык: UK ▾

  [ Шаблоны ]  [ История ]

  Все · Конгрессы · Визиты · Школа · Мои

  ┌────────────────────────────────────────────┐
  │ ✉  Письмо перед визитом к собранию          │
  │    Письмо · Клиндарий                       │
  │    UK  RU•  DE•        изменён 3 дня назад  │
  │                        [Изменён] [Открыть]  │
  └────────────────────────────────────────────┘
```

Точка после кода языка — перевода нет, работает fallback. Бейдж «системный»
отличает нетронутый шаблон от изменённого. Полный семишаговый композер
(шаблон → язык → источник данных → подстановка → правка → предпросмотр →
действие) остаётся, но только для входа из самого Documents — редкого.

### Редактор шаблона

Двухпанельный: слева текст, справа переменные, сгруппированные по namespace,
вставка кликом (механика уже есть — `insertAtCursor()` Конгрессов, переносим, а
не пишем заново). Снизу — живой предпросмотр на демо-данных: должно быть видно,
как выглядит письмо, а не как выглядит шаблон.

## 13. API

Синхронный после инициализации (обоснование — раздел 15, пункт 1):

```js
CWTemplates.list({ context: 'visit.congregation.letter', lang: 'uk' })
CWTemplates.get(id)
CWTemplates.render(id, data, lang)   // → { subject, body, pages, langUsed }
CWTemplates.save(id, patch)
CWTemplates.reset(id)                // удалить пользовательскую версию
CWDocuments.snapshot(rendered, ref, reason)
CWDocuments.listFor(ref)
```

**Нормализация — обязанность модуля.** Клиндарий отдаёт:

```js
{ congregation: { name, number, contactName, … },
  visit: { startDate, endDate, type } }
```

`CWTemplates` не знает про `entry`, `event`, `flags.f302`.

## 15. Риски

1. **Синхронность.** `letterHTML()` в Конгрессах синхронна, `CWDB` асинхронен.
   Наивное подключение даст мигание или пустое письмо. **Решение:**
   `CWTemplates` кэширует все шаблоны в память при `init()` (их десятки, не
   тысячи), API синхронный после готовности — тот же приём и по той же причине,
   что в `CWSender`.
2. **Cache-first service workers.** Правка `shared/templates.js` не дойдёт до
   вернувшихся пользователей без патч-бампа всех подключающих модулей.
   `check-versions.mjs` обязан пройти. Риск известный, но здесь он затрагивает
   сразу три модуля.
3. **`restoreDb` уничтожает общее.** `store.clear()` при восстановлении одного
   модуля снесёт `templates`/`documents`. Нужен `sharedDepends` в реестре
   модулей — та же проблема, что уже зафиксирована для справочника собраний;
   решать один раз для обеих задач.
4. **Необратимость `adopt()`.** У пользователей лежат отредактированные шаблоны.
   Перед миграцией — автоматический бэкап настроек модуля (`makeBackup()` в
   Конгрессах уже есть). `adopt()` читает значения до изменения флагов и
   вызывает `save()` немедленно.
5. **Два формата в одном движке.** Конгрессы — plain text с `**жирным**`,
   Клиндарий — HTML из RTE. HTML-шаблон, отрендеренный текстовым путём, покажет
   теги. Поле `format` обязательно, редактор переключается по нему.
6. **Расползание области.** Через полгода возникнет «пусть Documents хранит и
   список собраний, он же их подставляет». Правило «`templates` + `documents` и
   никаких других store» вынесено в `AGENTS.md`.
7. **Регрессия печати.** Все модули уже страдали от дрейфа селекторов
   `@media print` при переименовании классов. Любое изменение разметки письма —
   прогон печати Playwright'ом.

## 17. Структура файлов

```
shared/
  templates.js              ← движок + API (CWTemplates, CWDocuments)
  templates/
    builtin.js              ← системные шаблоны (текст в коде)
    namespaces.js           ← реестр переменных для панели вставки
  db.js                     ← +2 store, DB_VERSION 2

documents/
  index.html
  css/styles.css
  js/app.js
  js/editor.js              ← редактор шаблона (переносится из Конгрессов)
  js/composer.js
  i18n/dict.js
  icons/…, manifest.json, sw.js

docs/documents/
  00-proposal.md            ← этот документ
  01-audit.md               ← таблица находок с местами в коде
```

`documents/` следует паттерну остальных модулей (свой SW, manifest, иконки) —
новых паттернов не вводим. Но хранилище у него общее, в `shared/db.js`. Это не
нарушение правила «модуль не читает хранилище другого модуля»: `templates` —
изначально общий store, как `communities`.

## 18. Полный сценарий

**Дано.** Секретарь работает в польском интерфейсе. Язык документов —
украинский. Шаблон письма к собранию правился в марте.

1. Клиндарий, карточка визита **Prague East, 12–17 жовтня 2026**. Нажимает
   «Створити документ» → в меню три пункта из контекста `visit.congregation.*`.
2. Выбирает «Лист перед візитом». *Два клика, дальше только правки.*
3. Клиндарий нормализует данные и вызывает `CWTemplates.render()`. Движок берёт
   пользовательскую версию (мартовскую), колонку `uk`, подставляет `sender.*` из
   `shared/sender.js`, `congregation.*` и `visit.*` — из переданного объекта.
4. Предпросмотр: письмо плюс вторая страница «ПАМ'ЯТКА ДЛЯ КООРДИНАТОРА».
   Интерфейс вокруг польский, бумага украинская.
5. Секретарь дописывает абзац про парковку — правка идёт в **экземпляр**, шаблон
   не меняется.
6. «Друк» → snapshot в `documents`:
   `ref: { module:'circuit-planner', entity:'entry', id:'entry_31' }`,
   `reason:'print'`, `templateUpdatedAt` = мартовская отметка.
7. В календаре ничего не изменилось: `entry.start`, `end`, `eventId` — как были.
   Визит по-прежнему принадлежит Клиндарию.
8. **Декабрь.** Шаблон переписан. Секретарь открывает октябрьский визит →
   «Документи (1)» → видит тот самый текст с абзацем про парковку, а не новую
   редакцию.

Documents при этом ни разу не открывался как экран.

## 19. Решения Алекса (11.08.2026)

1. **Название модуля — «Документы» / `documents`.** Согласуется с рядом
   Конгрессы · Клиндарий · Школа пионеров · Назначения.
2. **Тема письма (`subject`) для Конгрессов — `null` до появления отправки.**
   Сейчас письмо печатается, а не отправляется; поле заводится в модели, но не в
   интерфейсе.
3. **`ru`/`de` шаблоны Конгрессов при миграции очищаются и помечаются
   `pending`.** Сейчас они притворяются переводом, будучи копией украинского.
   Пользователь увидит «перевода нет», а не «текст пропал»: fallback отдаёт `uk`.
   Тексты пишет носитель языка.
4. **Фаза 5 начинается с Клиндария.** У него больше типов документов, API
   проверится жёстче.
