## 1. Решения, уже принятые Алексом (28.09.2026)

1. **Вариант B.** Архив — отдельный модуль-хранилище со своей копией данных

2. **Школа пионеров вне области сейчас.** Модуль не подключается к Архиву в

3. **Записи (Журнал) не переносятся.** Журнал — рабочий, не закрытый архив;

4. **Назначения не названы Алексом ни в одну, ни в другую сторону** — see §7,

## 2. Терминологическая коллизия — до утверждения имени

Слово «архив» в кодовой базе уже занято **дважды**, оба раза — другим
понятием:

| Место | Что это | Где живёт |
|---|---|---|
| Архив выданных документов | Снимки писем/PDF, ПОКИНУВШИХ приложение (печать, отправка, экспорт). Общий для всех модулей рендерер, раздел «Архив» в UI Документов. | `shared/documents.js` (`CWDocs`), хранилище `CWDB.documents` |
| Архив Журнала | Архивация/восстановление узла дерева (`CWJournal.archive.list()`, `visits.archive/unarchive`), без каскада — своя, не связанная с закрытыми периодами семантика. | `journal/js/data.js` |

Новый модуль — **третье** значение: витрина закрытых по времени данных
(программы, визиты) с группировкой по служебному году. Понятия разные
(«документ ушёл» / «узел свёрнут» / «период закрылся»), но одинаковое слово в
интерфейсе рядом друг с другом — плитка хаба «Архив» и вкладка «Архив» внутри
Документов — читается как одно и то же и создаёт путаницу.

**Практическое следствие, а не просто именование:** новый модуль не должен
копировать в свой конверт то, что уже лежит в архиве документов (письма
конгресса участникам, письма Клиндария, S-302). Копирование удвоило бы
данные и развело бы два источника правды об одном и том же письме. Вместо
копии — **ссылка по `entityKey`** на существующую запись `CWDocs`, тот же
плоский ключ `module:entity:id`, которым архив документов уже пользуется.

**Открыто для решения Алекса** — как называть новый модуль в UI/коде, чтобы
не путать с этими двумя. Варианты вынесены в §8.

## 3. Что фактически лежит в модулях-источниках (проверено кодом)

Это ключевой вывод аудита: у Конгрессов и Клиндария **нет** набора отдельных
записей «программа» / «визит», которые можно просто пометить и скопировать
по одной. Есть один JSON-блоб на модуль.

### 3.1 Конгрессы (`congress-project`)

- Источник истины — `CWState.create('congress-project')` →
  `CWDB.state`, запись `{ id: 'congress-project', payload: '<JSON>' }`
  (`congress-project/js/state.js`).
- `payload` — весь прежний блоб localStorage целиком: задачи, участники,
  настройки, история автодополнения собраний. Внутренней структуры,
  которую БД знала бы сама, нет — знает только код модуля.
- Письма участникам архивируются отдельно и уже сейчас — через `CWDocs`
  (см. §2), в новый конверт не идут.
- Легаси-мост `congress-pwa-v34-speakers-backups` и `BACKUP_KEY` в
  localStorage — путь restore, не обычный источник чтения; для Архива
  нерелевантен.

### 3.2 Клиндарий (`circuit-planner`)

- Источник истины — тот же приём: `CWState` поверх `CWDB.state`, запись
  `circuit-planner`, легаси-ключ `service-year-planner-v9-4-2` остаётся
  путём восстановления при недоступной базе (`AGENTS.md`, `circuit-planner/
  AGENTS.md`).
- Блоб несёт календарь (`events[]`, записи визитов по неделям служебного
  года), S-302, черновики писем визита (`entry.emailBody` — сознательно НЕ
  архивируется, см. `docs/journal/documents.md`: черновик принадлежит
  визиту, а не архиву).
- **PIN-слой** (`localStorage['syp-pin-hash']`) — решение о слиянии с единым
  входом хаба не принято (`TODO.md`, Next). Архив, показывающий визиты
  Клиндария вне самого модуля, потенциально обходит этот PIN — см. §7,
  пункт 1. Это риск для observable behavior, значит по правилу «когда
  останавливаться» в `AGENTS.md` — решает Алекс, не код.

### 3.3 Документы (`documents`)

- Своих данных нет вообще (`documents/AGENTS.md`): модуль правит
  `CWDB.templates`. Архив документов (`CWDB.documents`) — общий слой,
  доступный из карточек других модулей, а не вотчина этого модуля.
- Для нового Архива это означает: секция «Документы» в новом модуле — это
  **тот же** `CWDocs`, показанный по служебным годам, а не отдельная копия.
  Раздел из плана Алекса («туда тоже в архив» для документов Школы) технически
  уже наполовину есть — снимки писем Школы уже пишутся в `CWDocs`
  (`pioneer-school` зарегистрирован в `sharedStores` с `documents`,
  `shared/backup.js:207-218`). Открыть их по служебному году в Архиве можно
  без подключения самого модуля Школы к контракту архивации.

### 3.4 Служебный год

- `shared/serviceyear.js` (6,6 КБ) уже выделяет понятие служебного года и
  используется Клиндарием. Ось группировки в Архиве («в архиве — данные
  конгресс, посещения») берёт готовую функцию, новой логики дат не нужно.

## 4. Из этого следует для формы конверта

Раз источник — блоб, а не запись, **владеет извлечением сам модуль**, а не
общий слой. Общий слой не может «просто скопировать визит»: он не знает, что
такое визит внутри чужого JSON.

> **Поправка 05.10.2026:** форма ниже предполагала, что Архив вызывает код
> модуля. Модули — отдельные страницы, поэтому конверт строит сам
> модуль-источник. Актуальный контракт — `05-archive-schema.md` §1.

Контракт по модулю (первоначальная форма, заменена):

```
list(serviceYear)     → какие сущности этого года можно архивировать
preview(entityId)     → что покажет карточка в Архиве
archive(entityId)     → конверт-снимок для копии
restore(envelopeId)    → вернуть в модуль (или отказ, если необратимо)
```

Конверт (единый для всех модулей): `{ id, sourceModule, entityType,
serviceYear, archivedAt, title, schemaVersion, payload, docRefs[] }`, где
`payload` — то, что вернул `archive()` модуля, а `docRefs[]` — ссылки
`entityKey` на уже существующие снимки `CWDocs` (см. §2), не их копии.

**Дублирование остаётся у источника до отдельного решения об удалении.**
Начинать со снимка без удаления исходных данных в модуле — тот же принцип,
что уже применялся к `state`/`documents` при миграции на общий слой
(`docs/journal/documents.md`, «Четыре правила необратимого переноса»):
копирование обратимо, удаление — нет, и их нельзя смешивать в одном шаге.

## 5. Хранилище

Новый store `CWDB.archive` (`keyPath: 'id'`, индексы как минимум
`sourceModule`, `serviceYear`, `entityType`) поднимает `DB_VERSION` c 6 до 7 —
чисто аддитивная схема, тот же характер апгрейда, что уже был у `journalNodes`
и соседей (`shared/db.js:82-97`, «Апгрейд 5→6 чисто аддитивный»).

Это подпадает под пункт 2 «Когда останавливаться» в `AGENTS.md` (схема
данных) — решение по факту уже принято Алексом выбором варианта B в §1, но
сам подъём версии — тот шаг, где по правилу проекта нужен `Opus 5 High`, а не
`Sonnet 5` (см. §9).

## 6. Бэкап и восстановление — обязательная часть плана, не последующая фаза

`docs/journal/documents.md` фиксирует уже дважды случившийся класс ошибки:
резервная копия одного модуля молча не увозила то, что было нужно для его
целостного восстановления (`cw-sender`, затем архив Конгрессов). Для нового
хранилища `archive` тот же риск: если store не попадёт в `sharedStores`
подходящих модулей или в полную копию хаба, восстановление даст «модуль есть,
архив пуст» без единой ошибки на экране.

Новый store должен быть добавлен в реестр `shared/backup.js` **в том же
заходе**, где заводится схема, не отдельной задачей потом. `scripts/
check-backup.mjs` — существующая проверка регрессии, ей это ловится, если
запись в реестре есть.

## 7. Открытые вопросы — решения Алекса (28.09.2026, второй заход)

1. **PIN Клиндария — не трогать.** Решение Алекса: вопрос не закрывается и не
   обходится в этой работе. Возможно, PIN со временем уберут целиком —
   отдельное будущее решение, не часть Архива. **Практическое следствие для
   контракта модуля (§4):** пока PIN жив, `circuit-planner.archive(entityId)`
   и любой показ его данных в Архиве обязаны проходить через тот же
   PIN-барьер, что и сам модуль — новый экран не создаёт себе более лёгкий
   путь к тем же данным. Реализация этого барьера — не в этой фазе, здесь
   только фиксация: закладывать проектирование Архива в расчёте на снятие
   PIN нельзя, он актуален до отдельного решения.
2. **Что делает архивацию визита/программы «прошедшей» — закрыто.** Решение
   Алекса: только ручное действие, окончательное решение всегда за ним.
   Приложение может **предложить** («этот визит похож на закрытый — отправить
   в архив?»), но не архивировать само. Предложение — подсказка в интерфейсе
   модуля-источника (например, у визита/программы прошлого служебного года),
   а не фоновая операция: пользователь видит кнопку и решает сам, отклонённое
   предложение не повторяется навязчиво.
3. **Назначения (`appointments`) — закрыто, вне области.** Решение Алекса:
   модуль архив не нужен вообще. Его роль — собрать письмо, сделать PDF,
   распечатать и отправить; данные не накапливаются по годам и не образуют
   «прошедшее» состояние, которое имело бы смысл откладывать. Модуль в
   контракт архивации (§4) не регистрируется.
4. **Имя модуля — закрыто.** Решение Алекса: новая плитка хаба называется
   «Архив». Существующий раздел внутри Документов теряет слово «архив» —
   остаётся «Документы» (или их внутренний список без отдельного заголовка
   «Архив»). Коллизия со вторым существующим значением (архив узлов
   Журнала — `CWJournal.archive.*`, §2) не переименовывается: там слово
   «архив» не вынесено в отдельный видимый раздел UI Журнала так, как оно
   было в Документах, риск путаницы там ниже.
