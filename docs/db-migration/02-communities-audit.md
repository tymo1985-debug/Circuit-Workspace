Дата: 16.08.2026. Основание — решение Алекса от 16.08.2026 о границе между
общим справочником и данными модуля.

Читать вместе с `01-audit.md` (общий трек миграции) и разделом
«Миграция на `shared/db.js`» в `AGENTS.md`.

---

## 1. Граница, утверждённая Алексом

> **Общий справочник — идентификация собрания. Модуль — то, как собрание
> выглядит в его собственном рабочем процессе.**

| В общий справочник (`CWDB.communities`) | Остаётся в модуле |
|---|---|
| `name` — название собрания | `color` — цвет метки в календаре |
| `congNumber` — номер собрания | `schedule` — расписание встреч |
| `address` | `visitType` — тип визита |
| `contactName` / `contactPhone` / `contactEmail` / `contactNote` | `formLanguage` — язык формуляра визита |

**Обоснование, сформулированное Алексом:** цвет и расписание помогают ему
различать типы и виды событий в календаре. Это свойство не собрания, а
представления собрания в конкретном модуле: если то же собрание завтра
откроют Конгрессы, зелёный цвет и «Ср 19:00» им не значат ничего, а название
и номер — значат.

**Практическое следствие, которое нужно удержать во всех фазах:** календарь
Клиндария после переезда обязан выглядеть и работать ровно так же. Из события
уезжает только идентификация, и та остаётся доступной через справочник.

### Решение по `lat`/`lng` (моё, отмечено отдельно)

Координаты кладу в общий справочник **вместе с адресом**. Они не отдельное
свойство, а машинная форма того же адреса: если адрес правят в одном модуле, а
координаты лежат в другом, они молча становятся враньём — тот же класс
рассинхрона, ради устранения которого затевается справочник. Конгрессы их
просто не используют; лишнее поле там ничего не стоит.

Если это не то, чего Алекс хотел, — правка дешёвая: убрать два поля из
`shared/directory.js` и из зеркала.

## 2. Клиндарий: `app.events[]`

Полноценная запись, на которую ссылаются записи календаря (`entry.eventId`) и
недели служебного года (`week.eventId`).

```js
{ id, name, color, address, schedule, visitType,
  contactName, contactPhone, contactEmail, contactNote,
  congNumber, lat, lng, formLanguage }
```

Точки записи (все три обязаны получить зеркало в фазе 5, шаг 3):

| Место | Что делает |
|---|---|
| `saveEventTemplate()` | создание и правка; собирает `payload` из полей формы |
| `deleteEventTemplate(id)` | удаляет событие + связанные записи календаря |
| `deleteAllEventTemplates()` | стирает весь справочник модуля |

Плюс два места нормализации, которые НЕ являются пользовательской правкой и
зеркалить их не нужно: приведение `events[]` при загрузке (`migrate`) и
`ensureEvent()` при импорте из легаси-формата.

**Идентификаторы стабильны** (`evt_*`, `evt_<slug>`), поэтому запись
справочника берёт `id` события как свой. Это делает шаг 4 (переключение
чтения) почти бесплатным: ссылки `entry.eventId` продолжают работать без
перекладывания.

**Ловушка, уже закрытая в модуле и важная для фазы 5:** `entry.title` —
это СНИМОК названия на момент создания записи, а не ссылка. При переименовании
события `saveEventTemplate` отдельно чинит записи, где `title` совпадал со
старым названием. Когда название переедет в справочник, эта логика обязана
поехать за ним, иначе переименование в другом модуле оставит в письмах и
формулярах старое имя — бесшумно.

## 3. Конгрессы: `settings.congregations[]`

Не справочник, а **история автодополнения**. Массив голых строк:

```js
congregations: ["EU-K-01", "SZ Warszawa",
                "Warszawa-Ukraiński-Południe (19588)", ...]
```

Как устроено:
- питает `<datalist id="congregationDatalist">` (`render.js`, `renderLists()`);
- поле собрания у участника — свободный текст, `task.participants[].congregation`;
- `saveEdit()` в `tasks.js` зовёт `addList("congregations", ...)` — то есть
  список **сам дописывается тем, что человек напечатал**;
- правится списком в textarea (`directories.js`, `openList`/`saveList`).

**Два вывода, определяющие форму шага 5:**

1. **Номер собрания вшит в название** — `«Warszawa-Ukraiński-Południe (19588)»`.
   Разбор строки в пару `{name, congNumber}` возможен, но он угадывание:
   скобки в конце названия не обязаны быть номером. Автоматическое
   расщепление без подтверждения человеком — недопустимо.
2. **Ссылок нет вообще.** Собрание у участника — копия строки, а не ссылка на
   запись. Перевод Конгрессов на `communityId` означал бы правку модели
   участника, всех писем и печатного плана. Это несоразмерно цели.

**Поэтому для Конгрессов предлагается не миграция, а подпитка:** datalist
собирается из объединения собственного списка и названий из общего
справочника. Данные модуля не трогаются вообще, а секретарь сразу получает в
автодополнении собрания, заведённые в Клиндарии. Обратная связь (напечатал
новое имя → появилось в общем справочнике) — отдельное решение, по умолчанию
НЕТ: иначе опечатки из свободного поля потекут в общий слой.

## 4. Школа пионеров

Собраний не хранит: в `registrationSchema.js` поля собрания нет. Учащийся
описан личными данными и параметрами учебника. Подключать её к справочнику в
фазе 5 нечего — но письмо учащемуся подписывается общим отправителем, так что
общий слой модулю уже не чужой.

---

## 5. Мёртвый код, который противоречит границе

`CWDB.importLegacyCommunities()` в `shared/db.js` копирует в общий слой
**все поля события подряд** — включая `color`, `schedule`, `visitType`,
`formLanguage`. Функция написана до решения о границе и **не вызывается
ниоткуда** (проверено поиском по всему репозиторию).

Оставить её как есть нельзя: это готовая ловушка для будущего захода — она
выглядит как штатный путь миграции и при первом же вызове занесёт в общий слой
ровно то, что решено там не держать. Приводится к границе в шаге 2.

## 6. Что из этого следует для шагов

- **Шаг 2** — `shared/directory.js` поверх существующего store `communities`
  (`CWDB` v5, индексы `name`/`congNumber` уже есть — версию базы поднимать не
  нужно). Синхронный API после `init()`, маячок в localStorage для соседних
  вкладок. Ни один модуль ещё не переключается.
- **Шаг 3** — Клиндарий пишет в оба места. `events[]` остаётся единственным
  источником чтения, поэтому шаг обратим целиком.
- **Шаг 4 (необратимый, отдельное подтверждение)** — чтение переезжает в
  справочник.
- **Шаг 5** — подпитка datalist Конгрессов.
- **Шаг 6** — сопоставление и дедупликация записей между модулями.

## 7. Открытые вопросы, которые нельзя решить в коде

1. **Удаление записи, известной двум модулям.** В шаге 3 введено поле
   `sources[]`: удаление в модуле убирает модуль из списка и стирает запись
   целиком только когда список опустел. Правильная ли это политика при живых
   ссылках из другого модуля — решать Алексу на шаге 4.
2. **Расщепление `«Название (19588)»`** — только с подтверждением человеком.
3. **Обратная запись из Конгрессов** в общий справочник — по умолчанию
   выключена (см. §3).
