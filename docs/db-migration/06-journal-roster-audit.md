## 1. Решения Алекса (05.10.2026)

1. Журнал не зависит от календаря: свой список собраний, групп и предгрупп,
   записи журнала опираются на него.
2. Вариант B: собственный список Журнала + одностороннее «Импорт из
   Клиндария».
3. Старые посещения НЕ перепривязываются.
4. Единый формат названия — только у собраний. Названия групп и предгрупп
   берутся как в календаре, без нормализации.
5. Новые данные обязаны попадать в общую резервную копию.
6. Обратной связи Журнал → календарь нет.

## 3. Что меняется

### 3.1. Экран «Состав» (только чтение)
- Новый пункт левого меню между «Районы» и «Задачи». Предлагаемое название —
  **«Состав района»**; три вкладки **Собрания / Группы / Предгруппы** и
  поиск по названию и номеру.
- Маршрут отдельный, одним роутером `route.js`; хвост строится по правилу
  «неполный хвост → ближайший валидный контекст».
- Источник — `CWJournal.nodes.byKind()`, имя — `canonicalName()`. Ничего не
  пишется, индекса и кэша нет.
- Строка ведёт в уже существующий экран собрания / группы.

### 3.2. Обзор
- Плашки считаются по `journalNodes` (активные узлы, архивные не считаются).
- Клик по плашке открывает соответствующую вкладку «Состава».
- `plannerView()` и зависимость Обзора от `CWPlanner.listCommunities()`
  убираются. Подписка `CWPlanner.subscribe` для плашек больше не нужна.
- Остаётся без изменений: слот J9a «посещение → запись Клиндария»
  (`CWJournal.planner`). Это связь посещения, а не состава, и она в
  решениях не затрагивалась.

### 3.3. Импорт из Клиндария (только по кнопке, только в одну сторону)
1. Кнопка «Импорт из Клиндария» на экране «Состав».
2. Источник — `CWPlanner.listCommunities()` плюс карточка `CWDirectory.get(communityId)`
   для номера и адреса. Статус `status()` не `ok/empty` → импорт
   недоступен, а не «ноль объектов».
3. Предпросмотр, три группы строк: **новые**, **уже есть**, **требуют решения**.
   Ничего не записывается до подтверждения.
4. Сопоставление «уже есть» — только по `communityId` (стабилен, не зависит
   от переименований). Совпадение по названию в «уже есть» не попадает.
5. Повторный импорт идемпотентен и **ничего не удаляет и не перезаписывает**.
   Объект исчез из календаря — узел остаётся.
6. Ручное создание собрания и группы в Журнале остаётся.

### 3.4. Названия
- **Собрание:** хранится `name` и `congNumber` отдельно (как в `CWDirectory`),
  отображение — «Имя (номер)». Если номер вшит в название календаря, а
  `congNumber` пуст, предлагается расщепление через `CWDirectory.parseName()`
  как догадка, которую подтверждает человек (правило из `03-matching-audit.md`).
- **Группа / предгруппа:** название как в календаре, без разбора и правки.
- Язык формуляра, цвет, тип визита в Журнал не переносятся (граница
  справочника, `02-communities-audit.md`).
- Расписание событий Клиндария (`events[].schedule`) — свободная строка. В
  `fields.schedule` (`midweek`/`weekend`) автоматически не раскладывается;
  можно предложить подстановку строкой только по явному клику, как уже
  сделано в диалоге расписания.

## 4. Группы и предгруппы: три проблемы

**П1. Нет родителя.** В календаре у группы нет родительского собрания, а
узел группы в Журнале обязан иметь родителем собрание (`assertValidParent`,
`kind`/`parentId` неизменяемы). Угадывать родителя по названию нельзя.
Решение: в предпросмотре у каждой новой группы выбор собрания-родителя
вручную. Название собрания в названии группы («…Hamburg-Russian-West») можно
показать как подсказку, но не применять. Без выбора родителя группа не
импортируется и остаётся в строке «ждёт родителя».

**П2. У узла группы нет ключа связи с календарём.** Сейчас `communityId`
есть только у собраний. Без него «уже есть» для группы определить нечем, а
повторный импорт создал бы дубликаты. Нужен `communityId` и у `group` /
`pregroup` (карточки для них в `CWDirectory` уже существуют: id события =
id карточки). Это **расширение схемы узла**, поэтому — решение D1 ниже.

**П3. Жизненный цикл источника `'journal'` в справочнике.** `countJournalRefs()`
(`districts.js`) считает ссылки только по `n.kind === 'congregation'`.
Если группы получат `communityId`, эту функцию надо расширить: иначе при
освобождении собрания `CWDirectory.detach(..., 'journal')` не увидит ссылку от
группы и может снять единственный источник у живой карточки. Это
проверяемый риск потери данных, поэтому он входит в обязательный чек R2.

## 5. Резервная копия

- **Новых хранилищ нет.** Импорт пишет в `journalNodes` и `communities`;
  оба уже в наборе записи `'journal'` в `shared/backup.js`. Реестр бэкапа
  не меняется, а значит `shared/*` не затрагивается и обязательного
  патч-бампа общего слоя нет.
- Узлы групп с `communityId` восстанавливаются вместе с карточками:
  `communities` в копии модуля сливается и не стирается, `journalNodes`
  заменяется целиком. Ссылка узла на карточку не может осиротеть при
  восстановлении собственной копии.
- Известная асимметрия остаётся: полная копия хаба, снятая до v6, узлов не
  содержит и их не очищает (`journal/AGENTS.md`, «Копия»).
- Обязательный прогон до выдачи R2/R3: копия → восстановление → проверка,
  что число узлов, их `communityId` и источники `'journal'` в карточках
  совпадают. Новая проверка в `scripts/` по правилу «этот класс багов уже
  ломался повторно» не нужна, пока тест укладывается в существующий
  roundtrip Журнала; решать на шаге R2.

## 6. Что НЕ меняется

- Посещения, записи, задачи, связи, проекты, защита J8: привязаны к `nodeId`,
  не к календарю. Перепривязка не нужна, риска для них нет.
- Слот J9a (`CWJournal.planner`) и глубокая ссылка `#calendar?entry=<id>`.
- `shared/*`, Клиндарий, `circuit-planner/app.js`: чтение через уже
  существующий `CWPlanner`, ни одной правки.
- Поиск J6: узлы уже ищутся; отдельный экран «Состав» ему не нужен.

## 7. Решения по открытым вопросам (05.10.2026)

- **D1 — да.** Узлы `group` и `pregroup` получают `communityId`; имя берётся из
  справочника, как у собраний. `countJournalRefs()` расширяется на все виды.
- **D2 — подсказка.** Родитель группы предлагается по названию, но применяется
  только после явного выбора человека.
- **D3 — вариант А.** Обзор считает только по журналу и календаря не читает.
  Разница «в календаре есть, в журнале нет» видна в строке «новые» предпросмотра
  импорта.

Название пункта меню («Состав района») и подстановка расписания по явному
клику — рабочие предложения, правятся без аудита.

## 8. Порядок работы (lowest risk first)

| Фаза | Что | Пишет в данные | Модель / effort |
|---|---|---|---|
| R1 | Экран «Состав», пункт меню, маршрут, плашки Обзора от Журнала, ключи i18n | нет | Sonnet 5 / Medium |
| R2 | `communityId` у групп и предгрупп, `countJournalRefs` для всех видов, ручная привязка группы к карточке, прогон бэкапа | да, схема узла | Sonnet 5 / High (Opus 5, если аудит R2 найдёт смену версии базы) |
| R3 | Импорт: предпросмотр, применение, идемпотентность, повторный прогон | да | Sonnet 5 / High |

R1 не пишет в данные. R2 и R3 меняют данные, перед каждой — отдельное подтверждение.
Каждая фаза — отдельная выдача, живой прогон 430×900 перед отдачей,
версия модуля Журнала поднимается по `docs/rules/release.md`.
