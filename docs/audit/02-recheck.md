Исправление сделано лучше, чем я предлагал: номер версии из файла копии в вычислении **не участвует вовсе** (`version = missing.length ? current + 1 : current`), хранилища создаются по описанию из дампа. Побочный выигрыш — копия, снятая на уже сломанной этим дефектом базе (v6), спокойно восстанавливается в здоровую v5. Плюс `prepareSchema()` зовёт `CWDB.init()` первым, поэтому в штатном случае поднимать версию не приходится вообще.

## 3. Новые находки

### CRITICAL

#### N-1. Тот же дефект версии IndexedDB остался для базы Школы пионеров

**Где.** `shared/backup.js`, функция `versionCeiling()`:

```js
function versionCeiling(name, dump, current) {
  if (name === SHARED_DB && global.CWDB && typeof global.CWDB.DB_VERSION === 'number') {
    return global.CWDB.DB_VERSION;
  }
  return Math.max(current, dump.version || 1);   // ← для баз модулей потолка фактически нет
}
```

Для общей базы потолок настоящий. Для `pioneer-school-db` потолком объявлена «схема, на которой снята сама копия» — но именно она и есть та величина, до которой база поднимается. Условие `version > ceiling` при этом никогда не выполняется, и защита не срабатывает.

**Воспроизведено:**

```
база Школы создана, версия: 2        (DB_VERSION модуля = 2)

--- ШТАТНОЕ восстановление копии Школы ---
restore: прошло
версия базы после: 2
открытие модулем (v2): OK
данные на месте: true                ← обычный путь в порядке

--- Копия из БОЛЕЕ НОВОЙ Школы (лишнее хранилище) ---
restore: ПРОШЛО
версия базы: 3 (была 2)
открытие модулем (v2): ОТКАЗ VersionError
```

**Почему это проблема.** Ровно та же необратимость, что в C-1, только другая база. `inspect()` тоже не помогает: проверка `schema-too-new` смотрит **только** на `SHARED_DB`:

```js
var dump = idb[SHARED_DB];       // базы модулей не проверяются
```

Последствие мягче, чем у общей базы, лишь по объёму: Школа теряет доступ к учащимся, классам, регистрациям, заместителям, учебникам и отзывам — всё, что у неё есть. Данные на диске целы, приложение их не видит, понизить версию нельзя. Наступает это в момент восстановления из копии, то есть когда человек уже в беде.

Сценарий реалистичен ровно настолько же, насколько тот, от которого защитились: копия сделана на устройстве с более новой версией Школы и восстанавливается на устройстве постарше.

**Серьёзность: CRITICAL.**

**Рекомендация (минимальная).** Отличить «призрачную базу» от «копии из будущего» можно без знания константы модуля: у призрачной базы, созданной `openExisting()` без версии, **ноль хранилищ**, а у настоящей — свои. Отсюда правило: поднимать версию базы модуля можно только когда хранилищ нет вообще.

```js
function versionCeiling(name, dump, current, existing) {
  if (name === SHARED_DB && global.CWDB && typeof global.CWDB.DB_VERSION === 'number') {
    return global.CWDB.DB_VERSION;
  }
  /* База модуля: его DB_VERSION этому коду недоступен (объявлен внутри
     модуля, а хаб его не грузит). Но подъём нужен ровно в одном законном
     случае — «призрачная» база v1 без хранилищ, созданная openExisting().
     Настоящая база с хранилищами, которой не хватает хранилища из копии,
     означает копию из более новой версии модуля. Ответ на неё — отказ. */
  return existing.length ? current : Math.max(current, dump.version || 1);
}
```

`existing` в `openForRestore()` уже вычислен, передать его — одна строка. И симметрично расширить `inspect()`, чтобы отказ наступал до первого изменения, как у общей базы: сравнивать `dump.version` не только для `SHARED_DB`, а для любой базы, чьи хранилища не покрываются текущей схемой.

**Риск исправления: низкий.** Штатный путь не меняется — воспроизведение выше показывает, что при совпадающих схемах `missing` пуст и ветка не исполняется. Обязательно: добавить в `check-backup.mjs` сценарий с базой модуля (сейчас там только `circuit-workspace-db`) и убедиться, что он **падает** на нынешнем коде.

### MEDIUM

#### N-2. Откат к предохранительному снимку идёт через тот механизм, ненадёжность которого его и породила

**Где.** `index.html`, обработчик кнопки `backupGuardBtn`:

```js
CWBackup.guard.get(newest.id).then(function (snap) {
  if (!snap) { say('backup.failed'); return; }
  CWBackup.download(snap, 'circuit-workspace-before-restore-…json');   // ← только файл
  say('backup.guard_saved');
});
```

**Почему это проблема.** Отдельная база `circuit-workspace-guard` заведена именно потому, что `download()` может отказать молча — блокировка автозагрузок, iOS Safari в режиме PWA, нет места, отменённый диалог. Это записано в шапке самой функции. Но единственный путь наружу у снимка — тот же `download()`. Там, где он не работает, кнопка отрапортует «снимок сохранён», файла не будет, а данные останутся в IndexedDB недосягаемыми для пользователя.

Комментарий рядом объясняет решение: «Отдельного пути восстановления намеренно нет: второй такой путь пришлось бы проверять и поддерживать наравне с первым». Возражение справедливо в общем виде, но здесь второго пути и не требуется — `CWBackup.restore(snap)` это **та же самая функция**, что вызывается после разбора файла. Пропускается только круг через файловую систему, а не проверенный код.

**Серьёзность: MEDIUM.** Страховка существует и цела; недоступна она ровно в тех условиях, ради которых заводилась.

**Рекомендация.** Оставить выгрузку файлом как основной путь и добавить вторую кнопку «Откатиться сейчас» → `CWBackup.guard.get(id).then(CWBackup.restore)` с тем же подтверждением, что и у обычного восстановления. Плюс честный ответ пользователю: `download()` не сообщает об успехе, поэтому текст «Снимок сохранён» лучше заменить на «Файл отправлен в загрузки. Если его там нет — воспользуйтесь кнопкой отката».

**Риск исправления: низкий** — переиспользуется существующий тракт восстановления.

## 5. Оценка проекта

**Как выглядит сейчас.** Из шестнадцати находок прошлого отчёта закрыто пятнадцать, шестнадцатая (M-4) закрыта наполовину. Ни одна не закрыта формально: везде, где я мог воспроизвести дефект, я воспроизвёл его заново и получил корректное поведение. Гейт вырос на восемь проверок, и каждая из восьми краснеет на сломанном входе — это редкий случай, когда набору проверок можно верить не на слово.

Два места оказались решены лучше, чем я предлагал: формула версии базы обошлась вовсе без номера из файла копии (и заодно чинит базы, уже сломанные прежним дефектом), а предохранительный снимок уехал в отдельную базу — я предлагал `snapshots`, что было ошибкой, полное восстановление стёрло бы его тем самым действием, от которого он страхует.

Найденный N-1 — не регресс, а **недоделанное исправление**: тот же класс дефекта в базе, до которой правка не дошла. Это ровно тот случай, ради которого повторный аудит и делается.

**Безопасен ли для развития — да, с одной оговоркой,** и оговорка стала меньше: раньше под угрозой была общая база всех модулей, теперь только база Школы.

**Риск ошибок при добавлении новых модулей — снизился заметно.** Гейт закрывает патч-бамп общего слоя, единственность моста локализации, единственность экранирования, реестр брейкпоинтов и отсутствие внешних скриптов. Это ровно те места, где новый модуль раньше мог тихо развести проект.

### Пять самых важных областей сейчас

1. **Потолок версии для баз модулей** — N-1, единственный необратимый путь.
2. **Достижимость предохранительного снимка** — N-2: страховка есть, до неё не дотянуться там, где она нужна.
3. **Вес запуска Школы** — N-3, самый тяжёлый модуль на самом слабом устройстве.

### N-1 — ЗАКРЫТО

Порядок был обратный привычному: сначала проверка, потом правка.

1. `scripts/check-backup.mjs`, сценарии **5.6 и 5.7**. Настоящая база Школы
   v2 с хранилищами `students`/`classes`, копия из более новой Школы с лишним
   `mentors`. На коде до правки **четыре утверждения красные**: восстановление
   проходило молча, версия базы уходила в 3, `opensAt(2)` возвращал
   `VersionError`, запись `s_keep` стиралась. Дефект воспроизведён внутри
   гейта, а не только в разовом сценарии.
2. `shared/backup.js`, `versionCeiling()` получил четвёртый параметр
   `existing`; возврат стал
   `(existing && existing.length) ? current : Math.max(current, dump.version || 1)`.
   Признак различения обоснован в комментарии: модули заводят все хранилища
   разом в одном `onupgradeneeded` (`STORES` в `pioneer-school/js/db.js` — 11
   штук), поэтому у настоящей базы набор полон для своей версии, и нехватка
   означает именно более новую схему, а не отложенное создание.
3. Сценарий 5.7 — регрессия: настоящая база плюс копия с тем же набором
   восстанавливается штатно. Без него правку можно было бы «починить»
   запретом на любое восстановление баз модулей.
4. Отдельное утверждение: при отказе по базе модуля `localStorage` цел.

**`inspect()` расширен не был, и это решение, а не пропуск.** Схема базы
модуля известна только после её открытия, то есть асинхронно; `inspect()`
синхронен и вызывается из `reader.onload`. Асинхронный `inspect()` завёл бы
второй путь отказа, который пришлось бы поддерживать наравне с первым — то
самое возражение, которым в проекте обоснован отказ от второго пути
восстановления. Отказ по базе модуля ловит фаза A (`openForRestore` →
`versionCeiling`), а она наступает **до первой записи куда бы то ни было**:
цена отказа там ровно такая же. Разница лишь в том, что до фазы A успевают
сняться предохранительный снимок и файл `before-restore`; данных ни то, ни
другое не меняет. Решение записано комментарием в самом `inspect()`.

**Подтверждение на настоящем IndexedDB.** `live-ceiling.mjs`, четыре профиля
в Chromium: настоящая база + копия из будущего, призрачная база, штатное
восстановление, регрессия общей базы. 11 из 11 зелёных. Гейт гоняет тот же
механизм на `fake-indexeddb`; теперь известно, что настоящая реализация ведёт
себя так же — прежде всего по `VersionError`, который подделка могла бы
имитировать неточно.

### N-3 — закрыта половина: проверка. Сам перенос остаётся

`scripts/check-lazy-pdf.mjs` переписан целиком. Было — три зашитых пути
Клиндария; стало — обход **всех модулей из реестра `shared/version.js`** и две
части:

- **храповик**: тяжёлой сторонней библиотеки в стартовой разметке быть не

сводки больше не создаёт впечатления, что класс закрыт целиком. Список можно

Добавлено утверждение «механизм догрузки найден хотя бы у одного модуля»:
