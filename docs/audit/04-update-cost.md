# Аудит 04 — стоимость обновления (P2-4)

**Дата:** 07.10.2026 · **База:** `33a7616` (хаб 0.42.43) · **Источник:** аудит 03, P2-4, фаза 7.
**Статус:** варианты и рекомендация. **Код не менялся — нужно решение Алекса.**

---

## 1. Что происходит сейчас

С 24.09.2026 (`update-pipeline-2026-09-24.md`, п. 3) имя кэша каждого модуля
содержит и версию модуля, и версию хаба: `journal-cache-v0.22.16-hub-0.42.43`.
Это не прихоть, а защита: worker модуля подключает `shared/version.js` через
`importScripts`, любой выпуск правит этот файл, браузер видит изменённый
worker и ставит новый. Без версии хаба в имени новый worker писал бы в кэш,
из которого ещё читает старый, и пользователь получал бы смесь файлов двух
выпусков (тот самый «сломанный интерфейс до жёсткого обновления»).

Следствие: **каждый выпуск = переустановка всех восьми worker'ов = заново
скачивается весь прекэш всех восьми**. Установка идёт с `cache: 'reload'`
(мимо HTTP-кэша — так задумано, P1-2), и неизменённые файлы качаются так же,
как изменённые.

нашлась новая версия: при нынешнем темпе — почти каждый день по ≈ 8,4 МБ,
восемь установок по 30–70 файлов. На мобильной сети это и деньги, и шанс
сорванной установки (тогда новая версия не встанет до следующей попытки —
безопасно, но обновление «не доезжает»).

## 3. Проверено и отброшено: условные запросы (ETag)

Первая мысль — при установке спросить сервер «изменился ли файл» и, если нет,
переложить старую копию. Не работает на GitHub Pages: проверено заголовками
живого сайта 07.10.2026 —

```
shared/vendor/jspdf.umd.min.js    etag: "6ac5ede5-58faf"   last-modified: 07 Oct 2026 06:59:49 GMT
shared/vendor/fontkit.umd.min.js  etag: "6ac5ede5-b92a8"   last-modified: 07 Oct 2026 06:59:49 GMT
```

ETag = время деплоя + размер (`0x6ac5ede5` — момент последнего push), а оба
файла не менялись неделями. Значит, после каждого деплоя у **всех** файлов
новый ETag, и условный запрос всегда ответит «изменился». По той же причине
бесполезно отказаться от `cache: 'reload'` в пользу HTTP-кэша: `max-age=600`,
дальше та же ревалидация по ETag.

Вывод: **отличать неизменённый файл можно только по содержимому, и знание об
этом должно ехать вместе с приложением.**

## 4. Варианты

### A. Перенос неизменённых файлов по хешу содержимого (рекомендуется)

- Генератор `scripts/build-precache-manifest.mjs` пишет
  `shared/precache-manifest.js`: адрес → короткий sha-256 содержимого для
  всех файлов всех прекэшей (≈ 207 записей, ≈ 12 КБ). Прецедент в проекте
  уже есть — `build-sri.mjs` / `sri-lock.json`, «правится генератор, а не
  вывод».
- Новый `shared/precache.js` (подключается в worker'ы через `importScripts`,
  как `offline-check.js`) заменяет `cache.addAll(...)` в `install`:
  1. открыть **новый** кэш (имя то же, что сейчас, — с версией хаба);
  2. для каждого адреса: если в одном из **своих** прежних кэшей лежит файл с
     тем же хешем — переложить его; иначе скачать с `cache: 'reload'`;
  3. последней записью положить в кэш карту «адрес → хеш» — она же признак
     завершённой установки и источник хешей для следующего выпуска;
  4. любой сбой → новый кэш удаляется целиком, установка проваливается,
     пользователь остаётся на прежней целой версии (атомарность P1-2
     сохраняется).
- Проверка гейта `check-precache-manifest.mjs`: манифест совпадает с
  пересчётом по файлам; каждый адрес каждого прекэша в нём есть.

**Что даёт.** По сети за выпуск — только изменённые файлы: в среднем
≈ 0,25 МБ вместо ≈ 8,4 МБ (**−95–97 %**), обычно 2–10 запросов вместо 379.
Установка короче — меньше шанс, что её оборвёт сеть.

**Что не меняет.** Имена кэшей, изоляция «старый активный / новый
ожидающий», порядок активации, баннер, рукопожатие версий, офлайн-
самопроверка, данные пользователя, IndexedDB, localStorage. Восемь
переустановок за выпуск остаются, но это локальное копирование, не сеть.

**Риски и защита.**
- *Устаревший манифест* (файл поменяли, генератор не запустили) → под новым
  хешем переложится старая копия → смешение версий, класс бага 24.09. Защита:
  проверка гейта красная при любом расхождении; по желанию — сверка хеша
  скачанного файла прямо в worker'е (`crypto.subtle`) с провалом установки
  при несовпадении. Побочный выигрыш сверки: ловит и уже существующий риск —
  край CDN, отдающий прошлую версию файла в первые минуты после деплоя.
  Цена сверки: в эти минуты установка будет проваливаться и повторится позже.
- *Первый выпуск с вариантом A:* у старых кэшей карты хешей нет → один раз
  полная загрузка, как сейчас. Дальше — экономия.
- *Пик места:* старый и новый кэш на время установки — как сейчас (≈ 2 × 18 МБ).
- *Клиндарий:* runtime-кэш (stale-while-revalidate) не трогается; переносится
  только статический прекэш.

**Объём.** `shared/precache.js` (~100 строк), 8 обработчиков `install`,
генератор, проверка гейта, расширение `live-update-pipeline.mjs` (вторая
синтетическая версия меняет один файл → по сети ровно он). Патч-бамп всех.
Модель: Opus 5 · High · Thinking On (service worker / кэш).

### B. Общий кэш неизменяемых файлов (vendor, шрифты) по содержимому

Один кэш `cw-immutable-…` на origin для 10 МБ библиотек, шрифтов и иконок;
модули его только читают. Убирает и повторную загрузку, и 6 МБ дублей на
диске. **Не рекомендуется сейчас:** ломает инвариант «каждый worker владеет
только своим префиксом» (кто и когда удаляет общий кэш? — нужна сборка
мусора между восемью worker'ами), усложняет `matchOwn()`, офлайн-самопроверку
и восстановление; чужие приложения того же origin (Current-Exchange)
добавляют риск. Выигрыш по сети после A — нулевой, остаются только 6 МБ диска.

### C. Разделить реестр версий: worker модуля не зависит от версии хаба

Каждый модуль подключает только свой файл версии; версия хаба уходит из имён
кэшей модулей; бамп модуля — только если изменились его файлы (это уже умеет
считать `check-shell-bump.mjs`). Выпуск с правкой одного модуля переустановит
один worker, а не восемь. **Не рекомендуется сейчас:** меняется контракт
обновления (`CW_MODULES`, рукопожатие `hub`, `release-manifest.js`,
оркестрация `checkAll/applyAll`, `check-versions`, `check-update-contract`,
живой прогон) — та самая область, которую чинили 24.09. После A переустановка
стоит копейки, и выигрыш C — время установки, а не трафик. Вернуться, если
восемь установок станут заметны по времени. Закрывает заодно техдолг
`release.md` §7.

### D. Реже выпускать (дисциплина, без кода)

Объединять несколько push в один выпуск. Ничего не стоит, но и не решает: при
13 выпусках в день пользователь всё равно получает один полный выпуск за
запуск. Полезно как привычка при любом варианте, не как замена.

## 5. Рекомендация

**A**, по желанию — со сверкой хеша скачанного файла в worker'е.
B и C — не сейчас; C записать в `IDEAS.md` как следующий шаг, если время
установки станет проблемой.
