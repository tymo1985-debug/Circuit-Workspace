## 1. Что представляет собой проект сегодня

Монорепо на GitHub Pages: один origin, хаб в корне, пять модулей папками уровнем ниже, общий слой в `shared/`. Vanilla JS, без сборки, без фреймворка. Шесть service worker'ов, шесть манифестов, две базы IndexedDB (`circuit-workspace-db` общая + `pioneer-school-db` своя у Школы), localStorage как легаси-хранилище и как синхронное зеркало.

**Что действительно хорошо и что не надо трогать:**

- **Гейт из 15 проверок — сильнейшая сторона проекта.** Он ловит расхождение версий по семи источникам, прекэш общего слоя, область кэша SW, сироты CSS-классов, дубли и пропуски ключей словарей, плейсхолдеры, инлайновые языковые таблицы, резервное копирование (33 утверждения). Немногие проекты этого размера имеют что-то похожее.
- **Локализация в отличном состоянии.** 1535 ключей, пять языков, **ноль пропусков, ноль кириллицы в en/pl/de, ноль пустых значений**. Проверено машинно, не на слово.
- **Разделение «язык интерфейса ≠ язык документа»** проведено последовательно, с отдельными атрибутами разметки и отдельным хранилищем. Это правильная и редкая архитектура.
- **Механизм обновления (`shared/update.js`)** сделан верно: ни один SW не зовёт `skipWaiting()` на установке, решение за пользователем, `controllerchange` защищён от первой установки.
- **Изоляция кэшей по префиксу** решена правильно во всех шести SW, `matchOwn()` вместо глобального `caches.match()` — тоже.
- **Комментарии в коде объясняют «почему», а не «что»,** и почти всегда с историей отказа, который к решению привёл. Это редкость и это надо сохранить.
- **Резервное копирование продумано глубоко:** декларативный реестр, частичная секция со слиянием, адресный отбор по `state`, отбор по префиксу для `snapshots`, `formatVersion` отдельно от версий приложения, предохранительная копия перед восстановлением.

Общий вывод по разделу: проект технически здоровый и заметно выше среднего. Найденные проблемы — точечные, а не системные.

### CRITICAL

#### C-1. Восстановление копии может навсегда сломать общую базу (`VersionError`)

**Где.** `shared/backup.js`, функция `restoreDb()`, строка вычисления версии:

```js
var version = Math.max(current, dump.version || 1) + (missing.length ? 1 : 0);
```

**Что происходит.** Если в файле копии есть хранилище, которого нет в базе на этом устройстве, версия базы поднимается **на единицу выше** версии из копии. Копия, снятая на устройстве с `DB_VERSION = 5`, поднимает базу до **6**. После этого `shared/db.js`, который всегда открывает базу с `DB_VERSION = 5`, получает `VersionError` и **не может открыть базу никогда** — понизить версию IndexedDB невозможно.

**Воспроизведено.** Два сценария, оба дают отказ:

```
Сценарий A — устройство со старым кэшем shared/db.js (база v3, 5 хранилищ):
  исходная версия базы: 3
  версия базы ПОСЛЕ восстановления копии v5: 6
  открытие через shared/db.js (DB_VERSION=5): ОТКАЗ VersionError

Сценарий B — свежее устройство (база создана как пустая v1 внутри openExisting):
  после openExisting (без версии): v1
  после восстановления копии v5: v6
  CWDB открыл бы с версией 5 → ОТКАЗ VersionError
```

Сценарий B особенно неприятен тем, что `openExisting()` без указания версии вызывается **самим механизмом копирования** — в `snapshot()`, то есть в предохранительной копии перед восстановлением. То есть подготовка к восстановлению создаёт условие, при котором восстановление ломает базу.

**Почему это проблема.** Последствия для пользователя выглядят как потеря данных, хотя данные на диске целы:

1. `CWDB` не открывается → `CWState.init()` ловит ошибку и честно отвечает «база недоступна».
2. Клиндарий и Конгрессы по правилу отката переходят **на прежний ключ localStorage** — а он, по решению фазы 2, остался снимком «как было на день переезда» (середина августа).
3. Пользователь видит своё состояние недельной давности, считает, что потерял данные, и начинает работать поверх старого снимка.
4. Расхождение накапливается. Даже когда `DB_VERSION` дорастёт до 7, в базе будет лежать одно состояние, а в старом ключе — другое, и слить их будет нечем.

Плюс молча теряются: архив выданных документов, шаблоны, справочник собраний, снимки истории — всё, что живёт только в общей базе.

**Серьёзность: CRITICAL.** Единственный найденный дефект, который приводит к необратимой для пользователя ситуации, и срабатывает он на пути «восстановление из копии» — то есть ровно тогда, когда человек уже в беде и надеется на этот механизм.

**Рекомендация (минимальная, одна функция).**

```js
// Версия базы после восстановления НИКОГДА не должна превысить ту, с которой
// её открывает shared/db.js — иначе CWDB получит VersionError навсегда.
var wanted = Math.max(current, dump.version || 1);
if (missing.length && wanted === current) wanted += 1;   // нужен onupgradeneeded
var ceiling = (name === 'circuit-workspace-db' && global.CWDB && global.CWDB.DB_VERSION)
  ? global.CWDB.DB_VERSION : Infinity;
if (wanted > ceiling) return Promise.reject(new Error('backup-newer-schema'));
var version = wanted;
```

Три части, каждая нужна:
1. `+1` только тогда, когда без него не попасть в `onupgradeneeded` — то есть когда `wanted` совпал с текущей версией. Это убирает сам дефект.
2. `shared/db.js` должен опубликовать `DB_VERSION` наружу (`CWDB.DB_VERSION = DB_VERSION;` — одна строка) — сейчас константа приватная.
3. Отказ с внятной причиной, если копия снята более новой версией приложения. Сегодня такая копия молча ломает базу; должна честно сказать «сначала обновите приложение».

Дополнительно — надёжнее и почти бесплатно: перед восстановлением общей базы позвать `CWDB.init()`, чтобы все хранилища схемы создались штатным путём. Тогда `missing` окажется пустым в подавляющем большинстве случаев и ветка вообще не понадобится.

**Риск исправления: низкий.** Правка локальна в одной функции одного файла, поведение при штатном восстановлении не меняется (там `missing` пуст и `version === current`). Обязательное условие: расширить `scripts/check-backup.mjs` сценарием «база старее копии» и убедиться, что проверка **падает** на текущем коде и проходит на исправленном — по вашему же правилу про сломанный вход.

### HIGH

#### H-1. Восстановление копии не атомарно: localStorage переписывается до IndexedDB

**Где.** `shared/backup.js`, `restore()`: `writeLocal(...)` вызывается синхронно внутри `forEach`, а задания на IndexedDB копятся в `jobs` и выполняются после.

**Почему это проблема.** `restoreDb()` отклоняется при `onblocked` — «IndexedDB заблокирована другой вкладкой». Это не экзотика: у пользователя PWA хаба и модуль часто открыты одновременно. К моменту отказа localStorage уже полностью заменён данными из файла, а базы — нет. Получается состояние, которого у пользователя никогда не было: настройки и легаси-ключи из копии, база текущая. Хаб покажет «backup.failed», но откатывать будет уже нечего.

Тот же класс: отказ на середине `Promise.all(jobs)` — одна база восстановлена, вторая нет.

**Серьёзность: HIGH.**

**Рекомендация.** Не переписывать архитектуру, а поменять порядок и добавить проверку готовности:
1. Сначала выполнить все задания IndexedDB, и только после их успешного завершения писать localStorage.
2. Перед началом проверить, что база открывается без `blocked` (пробное открытие с текущей версией и коротким сроком), и при отказе честно сказать «закройте другие вкладки приложения» **до** того, как что-либо изменено.

**Риск исправления: средний.** Порядок операций восстановления — чувствительное место; менять только вместе с расширением `check-backup.mjs` (проверка «отказ базы не оставляет localStorage переписанным»).

#### H-2. Предохранительная копия перед восстановлением не проверяется на успешность

**Где.** `index.html`, обработчик `fileInput.change`:

```js
CWBackup.snapshot().then(function (before) {
  CWBackup.download(before, 'circuit-workspace-before-restore-…json');
  return CWBackup.restore(snap);   // выполняется независимо от того, сохранился ли файл
})
```

**Почему это проблема.** `download()` создаёт `<a download>` и кликает по нему. Браузер может отказать: блокировка автоматических загрузок, iOS Safari в режиме PWA, отсутствие места, отменённый пользователем диалог. Функция ничего не возвращает и не бросает — восстановление продолжится, и обещанный откат не будет существовать. Комментарий рядом гласит «если файл окажется не тем, откатиться будет нечем» — именно этот случай и не закрыт.

**Серьёзность: HIGH** (обесценивает единственную страховку перед необратимой операцией).

**Рекомендация.** Минимальный вариант — не полагаться только на файл: положить предохранительный снимок ещё и в хранилище `snapshots` общей базы под ключом `restore:<timestamp>` (механизм уже есть, `CWSnapshots`), и только потом восстанавливать. Тогда откат существует даже при неудачной выгрузке. Второй шаг — явное подтверждение пользователя «файл сохранён, продолжить?» перед необратимой частью.

**Риск исправления: низкий.** Добавление, а не изменение существующего пути.

#### H-3. Данные подставляются в HTML-шаблон без экранирования

**Где.**
- `shared/templates.js`, `render()`: `return String(value);` — подстановка без экранирования, независимо от того, текстовый шаблон или HTML.
- Результат уходит в `innerHTML`: `circuit-planner/app.js:3844` (`composerPaper.innerHTML = built.bodyHtml …`), `documents/js/app.js:471`.
- И в `document.write` окна печати: `shared/print.js:227`, вызывается из `circuit-planner/app.js:3957` (`html: … + body`, где `body` — `doc.bodyHtml`).

**Почему это проблема.** Значения приходят из пользовательских данных: название собрания, адрес, имя контакта, номер собрания. Эти данные попадают в приложение тремя путями, и два из них внешние:
- восстановление резервной копии — файл, который пользователь пересылает себе почтой и хранит в облаке;
- импорт PDF (Школа) и импорт легаси-данных.

Название собрания вида `<img src=x onerror="…">` выполнится в контексте origin приложения при первом же предпросмотре письма. Окно печати открывается как `about:blank` — **тот же origin**, с доступом к `opener`, то есть ко всему localStorage и обеим базам IndexedDB.

Даже без злого умысла: любой символ `<` в названии собрания ломает вёрстку бумаги молча.

Правило 3 движка («подставленное значение дальше не сканируется») закрывает рекурсию шаблонов, но не закрывает разметку.

**Серьёзность: HIGH.** Локальное приложение, вектор требует импорта чужого файла — но последствия максимальные, а данные пользователя здесь чувствительные (адреса, телефоны, почта собраний).

**Рекомендация.** Не менять правила движка, а добавить осведомлённость о формате:

```js
render: function (template, data, options) {
  var escape = options && options.escape === true;   // по умолчанию поведение прежнее
  …
  return escape ? escapeHtml(String(value)) : String(value);
}
```

и передавать `{ escape: true }` там, где шаблон объявлен `format: 'html'` — это Клиндарий (`substitutePlaceholders`) и предпросмотр в Документах. Текстовые шаблоны (Конгрессы, Школа) остаются как есть: их результат и так проходит через `escapeHtml`/`<pre>`.

Экранировать нужно **значения**, а не шаблон: сам шаблон — авторская HTML-разметка пользователя, и её ломать нельзя.

**Риск исправления: средний.** Затрагивает вид готовых писем. Проверять побайтным сравнением письма до и после на данных без спецсимволов (должно совпасть) и на данных со спецсимволами (должно измениться в лучшую сторону).

#### H-4. Семь внешних скриптов с CDN без `integrity`

**Где.**
- `circuit-planner/index.html:808–811` — jsPDF, jspdf-autotable, pdf-lib, fontkit
- `pioneer-school/index.html:442–444` + worker на 447 — jsPDF, pdf.js, xlsx
- `pioneer-school/register.html:103` — jsPDF

Ни одного атрибута `integrity`, ни одного `crossorigin`. Проверено: `grep integrity` по всем HTML — ноль совпадений.

**Почему это проблема.** Это единственный путь, которым в приложение может попасть чужой код. Компрометация cdnjs или jsdelivr (или подмена на пути — в кафе, в гостинице, в чужой сети) даёт исполнение произвольного кода с полным доступом к обеим базам и localStorage: адреса, телефоны, почта собраний, весь архив писем.

Отдельно усугубляет то, что **оба service worker'а кладут ответ CDN в свой кэш**: `circuit-planner/sw.js` прекэширует четыре CDN-URL на установке, `pioneer-school/sw.js` — четыре своих. Подменённый один раз файл остаётся в офлайн-кэше пользователя навсегда, переживая перезагрузки и переустановки страницы.

**Серьёзность: HIGH.** Вероятность события низкая, цена максимальная, а исправление — самое дешёвое во всём отчёте.

**Рекомендация. Два варианта, второй лучше.**

1. **Быстрый:** добавить `integrity="sha384-…"` и `crossorigin="anonymous"` ко всем семи тегам. Полчаса работы, риск близок к нулю, ломает ровно ничего. Важно: SRI не защищает `pdf.worker.min.js`, который подставляется через `GlobalWorkerOptions.workerSrc` — его придётся положить локально.
2. **Правильный:** сложить библиотеки локально, как уже сделано в `pioneer-school/js/vendor/` для pdf-lib и fontkit. Тогда исчезает и CDN-риск, и зависимость первого запуска от сети, и дубль (см. M-3).

**Риск исправления: очень низкий** для варианта 1, низкий для варианта 2 (нужен патч-бамп модулей и правка прекэша SW — тот самый диф, который обязан быть строго дополняющим).

#### H-5. Правило «правка `shared/*` = патч-бамп модулей» ничем не проверяется

**Где.** Правило описано в `AGENTS.md:1600` и в шапках всех SW. Гейта под него нет.

**Почему это проблема.** Четыре из пяти модулей — `congress-project`, `pioneer-school`, `appointments`, `documents` — читают из своего кэша **чистым cache-first без фоновой ревалидации**:

```js
const cached = await matchOwn(request);
if (cached) return cached;        // сеть даже не опрашивается
```

Имя кэша содержит версию модуля. Значит правка `shared/style.css` или `shared/db.js` без патч-бампа модуля **не доедет до пользователя никогда** — он останется на старой копии общего слоя до следующего бампа этого модуля, сколько бы месяцев ни прошло.

Ровно этот класс отказа уже случался 11.08.2026 («старый `app.js` из кэша рядом с новой разметкой») и описан в шапке `shared/update.js` как причина его появления. Сейчас единственная защита — человеческая память, а объём общего слоя вырос до 24 файлов.

Хуже того, это же условие делает возможным сценарий C-1: устройство с устаревшим кэшем `shared/db.js` и более новой копией — источник расхождения версий схемы.

Исключение — Клиндарий: у него stale-while-revalidate, он свежий общий слой подхватит сам.

**Серьёзность: HIGH** (это метапроблема: она умножает вероятность всех остальных).

**Рекомендация.** Новая проверка `scripts/check-shared-bump.mjs` в `check-all.mjs`:

- взять `git diff --name-only HEAD~1 HEAD` (или сравнение с `origin/main`);
- если среди изменённых есть `shared/*` — потребовать, чтобы у каждого кэш-фёрст модуля, чей прекэш содержит этот файл, версия в `CW_MODULES` отличалась от версии в предыдущем коммите;
- новый файл общего слоя из правила исключить (обоснование уже записано в `AGENTS.md:1599`).

Проверку обязательно прогнать на сломанном входе: правка `shared/style.css` без бампов должна дать красный.

**Риск исправления: нулевой** — это добавление проверки, кода приложения она не касается.

### MEDIUM

#### M-1. `Promise.all(...).then(App.init)` без `.catch()`

**Где.** `circuit-planner/app.js`, конец файла:

```js
Promise.all([
  App.store.remote.init(),
  App.store.history ? App.store.history.init() : Promise.resolve(false),
  self.CWDirectory ? self.CWDirectory.init() : Promise.resolve(false),
]).then(() => App.init());
```

**Почему это проблема.** Сегодня безопасно: проверено чтением — все три `init()` ловят свои ошибки и никогда не отклоняются. Но защита держится на внутренней дисциплине трёх файлов общего слоя. Один будущий `throw` или один пропущенный `.catch()` внутри `CWSnapshots.init()` означает, что `App.init()` не вызовется вообще — **Клиндарий не откроется, экран останется пустым, в консоли будет только unhandled rejection.** Самый дорогой класс отказа в проекте, и стоит он одной строки.

**Серьёзность: MEDIUM** (сейчас не дефект, а архитектурный риск).

**Рекомендация.** `.then(() => App.init(), (e) => { console.error('Клиндарий: подготовка общего слоя сорвалась', e); App.init(); })` — модуль обязан открыться в любом случае, пусть и на прежнем ключе.

**Риск исправления: нулевой.**

#### M-2. Версия модуля объявлена в двух местах у Конгрессов и Школы

**Где.** `congress-project/service-worker.js:5` (`const APP_VERSION='4.46.6'`), `pioneer-school/js/app.js` + `pioneer-school/sw.js` (по своему `APP_VERSION`), плюс запись в `shared/version.js`.

**Почему это проблема.** `check-versions.mjs` сверяет семь источников и расхождение поймает — это хорошая страховка. Но страховка не то же самое, что единственный источник: при каждом выпуске правится 2–3 места вместо одного, и проверка ловит ошибку только если её запустили. Клиндарий уже сделан правильно:

```js
importScripts('../shared/version.js');
const APP_VERSION = self.CW_MODULES['circuit-planner'].version;
```

Побочный выигрыш этого приёма важнее, чем кажется, и он описан в `circuit-planner/sw.js`: браузер при проверке обновления сверяет не только сам `sw.js`, но и импортированные им скрипты — значит **любой** выпуск, поднимающий версию в реестре, сам инвалидирует кэш модуля.

**Серьёзность: MEDIUM** (технический долг с заметным риском при выпуске).

**Рекомендация.** Перевести четыре оставшихся SW на `importScripts('../shared/version.js')` по образцу Клиндария. Для `pioneer-school/js/app.js` — читать из `CW_MODULES` там же, где уже читается в `js/i18n.js` (`self.CW_MODULES[this.MODULE].version`).

**Риск исправления: низкий**, но именно эта правка меняет поведение установки SW — обязателен живой прогон установки и обновления каждого модуля.

#### M-3. Дубли библиотек PDF

**Где.**
- `pdf-lib@1.17.1` — CDN у Клиндария, локальная копия `pioneer-school/js/vendor/pdf-lib.min.js` (513 КБ)
- `fontkit@1.1.1` — CDN у Клиндария, локальная копия `pioneer-school/js/vendor/fontkit.umd.min.js` (741 КБ)

**Риск исправления: средний** — трогает тракты выдачи PDF в двух модулях. Проверять реальным `page.pdf()` с обратным извлечением текста, как уже принято в проекте.

#### M-4. Клиндарий грузит ~4,5 МБ JS на каждый запуск ради экспорта PDF

**Где.** `circuit-planner/index.html:808–818`.

Измерено:

| Что | Размер |
|---|---|
| `forms/s302-form.js` | 748 КБ |
| 4 × `fonts/fonts-aptos-*.js` | 1 200 КБ |
| `app.js` | 415 КБ |
| `i18n/dict.js` | 192 КБ |
| остальное локальное | ~480 КБ |
| **локально итого** | **~3 036 КБ** |
| CDN (jsPDF + autotable + pdf-lib + fontkit) | ~1 500 КБ |
| **всего на холодный запуск** | **~4,5 МБ** |

Для сравнения: хаб ~296 КБ, Конгрессы ~287 КБ, Школа ~1 777 КБ.

**Рекомендация.** Ленивая догрузка PDF-стека по требованию: одна функция `ensurePdfStack()`, которая вставляет `<script>` и возвращает промис, вызываемая из кнопок выдачи PDF и формуляра S-302. Файлы остаются в прекэше SW — офлайн не страдает, но старт перестаёт их разбирать.

**Риск исправления: средний.** Затрагивает четыре тракта выдачи бумаг. Делать одним шагом, отдельным выпуском, с живым прогоном каждого тракта. **Не начинать раньше, чем закрыты P0 и P1** — это улучшение, а не исправление.

#### M-7. Мост локализации написан почти одинаково в каждом модуле

**Где.** `congress-project/js/i18n.js`, `pioneer-school/js/i18n.js` и такие же блоки внутри `appointments`/`documents`/`circuit-planner`.

Совпадает почти построчно: `MODULE`, `HUB_VALUE = '__hub'`, `ready()`, `t()`, `isInherited()`, `currentValue()`, `choose()`, `applyTitle()`, `fillSelect()`, `init(rerender)`, подписка на `onChange`, обработчик `change` у `<select>`.

**Почему это проблема.** Одна задача решена пять раз. Исправление ошибки в разрешении языка или в заполнении селектора требует пяти правок, а гейт совпадение не проверяет. Различаются файлы только именем модуля, id элемента селектора и ключом заголовка — то есть параметрами, а не логикой.

**Серьёзность: MEDIUM** (технический долг; рабочего дефекта нет).

**Рекомендация.** `CWI18n.bindModule({ module, selectId, titleKey, onChange })` в общем слое; модульные файлы сокращаются до вызова плюс своя специфика (`tStatus` у Конгрессов, `T` у Школы — они действительно разные и должны остаться). Делать **после** P0/P1: это чистое улучшение читаемости, и оно требует патч-бампа всех пяти модулей.

**Риск исправления: средний** — трогает старт каждого модуля.

## 3. Ответы на конкретные вопросы задания

**Дублирующаяся логика.** Найдено три очага: мост i18n (M-7), `escapeHtml` (M-8), адаптивная таблица (M-5). Всё остальное, что выглядит как дубль, дублем не является — модульные `js/i18n.js` и `js/doclang.js` это тонкие мосты, а не вторые реализации, и в них это явно оговорено.

**Разные источники одних и тех же данных.** Не найдено ни одного. Отправитель — только `cw-sender`. Язык интерфейса — только цепочка `CWI18n`. Язык документа — только `CWDocLang`. Версии — реестр `CW_MODULES` со сверкой семи источников гейтом. Служебный год — `shared/serviceyear.js` с делегированием. Единственное дублирование источника — версии модулей в SW (M-2), и оно под контролем проверки.

**Конфликтующие `storageKey`.** Проверены все ключи и все префиксы кэшей — **пересечений нет**:

```
cw-lang / cw-lang:<module>        cw-doclang / cw-doclang:<module>
cw-sender    cw-backup-log        cw-directory-rev
cw-state-mirror:<m>  cw-state-rev:<m>
service-year-planner-v9-4-2 (+ -history, -accent)   syp-pin-hash
congress-pwa-v34-speakers (+ -backups)              cw-appointments-v1
cw-congress-sidebar-collapsed
кэши: circuit-workspace-shell-v · congress-pwa- · syp-static-v / syp-runtime-v ·
      pioneer-school-cache-v · appointments-cache-v · documents-cache-v
```

**Опасные зависимости между модулями.** Ни один модуль не читает хранилище другого — правило соблюдается. Единственный канал влияния — общий слой, и он под контролем: `state` выгружается адресно, `snapshots` по префиксу, частичная секция восстанавливается слиянием. Проверено 33 утверждениями `check-backup.mjs`, включая «состояние соседнего модуля не тронуто восстановлением».

Реальная связь между модулями одна и она не в данных: **правка `shared/*` без патч-бампа ломает соседей молча** (H-5).

**Может ли изменение одного модуля сломать другой.** Только через общий слой и только описанным в H-5 способом. Внутри модуля — нет.

**Насколько легко добавить новый модуль.** Легко и это заслуга архитектуры. Обязательный минимум из шести пунктов записан в `ARCHITECTURE.md §5`, `backup.js` требует одной записи в `MODULES`, гейт проверяет плитку, манифест, прекэш, область кэша и версию. Единственное, что придётся написать заново, — мост i18n (M-7).

**Legacy-код.** Найденное: раздел 5.6 `shared/style.css` (M-5); `importLegacyCommunities()` в `db.js` — помечена как «разовый импорт для служебных сценариев», предпочтительный путь `CWDirectory.upsert()`, оставлять сознательно можно; ветки чтения `syp-static`/`syp-runtime` без версии в `circuit-planner/sw.js` — нужны, кэши до 9.66.0 у пользователей ещё живут. Мёртвого кода в объёмах, требующих чистки, нет.

**Переживает ли приложение обновление версии.** Да, механизм `shared/update.js` сделан правильно и это одна из сильных частей проекта. Смеси старого JS с новой разметкой после обновления GitHub Pages **не будет**: `skipWaiting()` на установке убран во всех шести SW, страница живёт на том наборе файлов, с которым запустилась, перезагрузка только по кнопке. Единственная брешь ровно одна — H-5.

**Долгая работа на старой версии.** `CWUpdate.init()` зовёт `reg.update()` при каждом старте, кнопка в шапке хаба форсирует проверку всем регистрациям origin разом. Закрыто.

**Полная перезагрузка браузера / временное отсутствие сети.** Отработано: прекэш покрывает весь общий слой в каждом модуле (стережёт `check-shared-precache.mjs`), офлайн-фолбэк на `index.html` только для `mode === 'navigate'` (важная деталь — раньше HTML отдавался в ответ на любой упавший запрос), `Response.error()` вместо `undefined` в `respondWith`. Единственное, что не работает офлайн на **первом** запуске Школы, — CDN-библиотеки, если сети не было в момент установки SW; помечено комментарием и подхватывается в рантайме.

**Импорт/экспорт.** JSON-копии — разобраны выше. CSV — **защита от формульной инъекции есть и сделана правильно** (`ExcelExport._escape`: `/^[\t\r]*[=+\-@]/` → префикс `'`), в XLSX намеренно не применяется и это верно. XLSX через SheetJS — текстовые ячейки. PDF-импорт через pdf.js — данные попадают в поля и оттуда в CSV/DOM, то есть подпадают под H-3. `mailto:`-ссылки в `register.html` полностью проходят `encodeURIComponent` — чисто.

**Печать и документы.** `shared/print.js` — самая аккуратная часть проекта: старт по готовности окна с двумя кадрами после `load`, страховочный таймер 3 с, `@page` объявляет сам документ (иначе предпросмотр расходился с бумагой), защита от двойного `beforeprint`, отказ вместо печати экрана при заблокированном окне. Разрывы страниц через `.pb`, альбомная ориентация для календаря объявляется вызывающим. `check-print-ready.mjs` в гейте. Претензий по существу нет, кроме L-6 и H-3.

**Производительность.** Замеры в M-4. Отдельно отмечу то, чего искать не пришлось: `CWPersist` (дебаунс 400 мс с потолком 2000 мс) снимает частую запись, `CWDB.eachByIndex` читает снимки курсором и берёт только шапку вместо `getAll()` — это правильное решение ровно того класса задач, где обычно и растёт время открытия. Тяжёлых циклов и повторных загрузок одних данных не найдено. Основная и практически единственная цена — M-4.

## 5. Оценка проекта

**Технически здоров.** Гейт из 15 проверок, полное покрытие пяти языков без единого пропуска, продуманное разделение слоёв, комментарии, объясняющие причину каждого решения через историю отказа, который к нему привёл. Это заметно выше среднего уровня для проекта такого размера, и это не комплимент, а наблюдение по коду.

**Безопасен ли для дальнейшего развития — да, с одной оговоркой.** Оговорка — P0: пока `restoreDb()` не поправлен, у пользователя есть путь необратимо потерять доступ к данным, и путь этот пролегает через механизм, к которому обращаются в беде. Всё остальное можно развивать параллельно.

**Масштабируемость архитектуры — высокая.** Добавление модуля описано, проверяется гейтом и стоит одной записи в трёх реестрах. Единственное, что придётся дописать руками, — мост i18n (M-7), и это устранимо.

**Риск ошибок при добавлении новых модулей — умеренный,** и почти весь он сосредоточен в одном месте: правка общего слоя без патч-бампа кэш-фёрст модулей (H-5). Закрытие H-5 гейтом снижает этот риск сильнее, чем любая другая одиночная мера в отчёте.

### Пять самых важных областей сейчас

1. **Целостность восстановления резервной копии** — единственный необратимый путь (C-1, H-1, H-2).
2. **Механизм доставки правок общего слоя** — H-5; он умножает вероятность всего остального.
3. **Экранирование данных на границе «данные → разметка»** — H-3 + M-8.
4. **Внешние зависимости** — H-4 + M-3: самая дешёвая правка с самой высокой ценой отказа.
5. **Вес запуска Клиндария** — M-4: единственная заметная пользователю проблема качества, не связанная с корректностью.

## Recommended next step

**Начать с C-1: потолок версии IndexedDB в `restoreDb()`.**

Почему именно с него, а не с чего-то более заметного:

1. Это **единственный найденный дефект с необратимым исходом**. Всё остальное чинится следующим выпуском; этот — не чинится вовсе, потому что понизить версию IndexedDB нельзя.
2. Он **воспроизведён**, а не выведен из чтения кода. Сценарий готов и его можно превратить в проверку гейта за один заход.
3. Правка **изолирована**: три строки в одной функции `shared/backup.js` плюс одна строка публикации константы в `shared/db.js`. Ни архитектуры, ни хранилищ, ни `storageKey` она не касается. При штатном восстановлении (`missing` пуст) поведение не меняется вообще.
4. Он **блокирует смежные работы**: `ROADMAP.md` ставит перевод Конгрессов и Клиндария на `shared/db.js` в зависимость от `sharedDepends` в `restoreDb`. Трогать `restoreDb` всё равно придётся — разумнее сделать это, когда механизм заведомо корректен.

**Предлагаемый порядок одного захода:**

1. Расширить `scripts/check-backup.mjs` сценарием «база старее копии»: восстановить копию с `version: 5` в базу v3 и потребовать, чтобы после этого `indexedDB.open(name, 5)` открывалась. **Убедиться, что проверка падает на текущем коде** — иначе ей нельзя верить.
2. Опубликовать `CWDB.DB_VERSION` (одна строка в `shared/db.js`).
3. Поправить вычисление версии в `restoreDb()` + отказ `backup-newer-schema` с локализованным сообщением в хабе.
4. Прогнать `check-all.mjs` — должно стать 16/16.
5. Живой прогон восстановления в Chromium: полная копия хаба и копия одного модуля, обе на чистом профиле и на профиле с данными.
6. Патч-бамп: `shared/backup.js` и `shared/db.js` лежат в прекэше всех пяти модулей — бампаются все пять плюс хаб.

Дальше — H-4 (`integrity`, полчаса и почти нулевой риск) и H-5 (гейт на патч-бамп), после чего можно возвращаться к запланированным трекам.
